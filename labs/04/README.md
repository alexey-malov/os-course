### Задание 1 — Банковские переводы: поиск и устранение гонок — **40 баллов**

Вам предоставлена программа, моделирующая переводы денег между банковскими счетами.

В банке открыто **1000 счетов**, на каждом из которых первоначально находится **1 000 000 рублей**.

Для хранения баланса используется `int64_t`.

Программа запускает **10 потоков**, каждый из которых выполняет **1 000 000 попыток перевода**
случайной суммы между двумя случайными различными счетами.

Если на исходном счёте недостаточно средств, перевод не выполняется.

После завершения всех рабочих потоков главный поток проверяет два инварианта:

1. Баланс каждого счёта неотрицателен.
2. Общая сумма денег на всех счетах равна первоначальной — **1 000 000 000 рублей**.

Исходная программа не использует механизмов синхронизации и может работать некорректно.

#### Исходный код программы

[Запустить программу на godbolt.org](https://godbolt.org/z/dbMbPxWeY)

```cpp
#include <algorithm>
#include <chrono>
#include <cstddef>
#include <cstdint>
#include <functional>
#include <iostream>
#include <numeric>
#include <random>
#include <thread>
#include <vector>

using Money = std::int64_t;

constexpr std::size_t AccountCount = 1'000;
constexpr Money InitialBalance = 1'000'000;
constexpr int ThreadCount = 10;
constexpr int TransfersPerThread = 1'000'000;
constexpr Money MaxTransferAmount = 1'000'000;

// Пытаемся перевести деньги с одного счёта на другой
void Transfer(std::vector<Money>& balances,
              std::size_t from, std::size_t to, Money amount)
{
    if (balances[from] >= amount) // Нельзя перевести больше, чем имеется
    {
        balances[from] -= amount;
        balances[to] += amount;
    }
}

void Worker(std::vector<Money>& balances, unsigned workerId)
{
    // Каждый поток использует свой собственный генератор случайных чисел
    std::mt19937_64 random{0xC0FFEEu + workerId};
    std::uniform_int_distribution<std::size_t> accountDist(0, balances.size() - 1);
    std::uniform_int_distribution<Money> amountDist(1, MaxTransferAmount);

    for (int i = 0; i < TransfersPerThread; ++i)
    {
        const auto from = accountDist(random);
        auto to = accountDist(random);
        while (to == from)
        {
            to = accountDist(random);
        }

        Transfer(balances, from, to, amountDist(random));
    }
}

int main()
{
    std::vector<Money> balances(AccountCount, InitialBalance);
    const Money expectedTotal = static_cast<Money>(AccountCount) * InitialBalance;

    const auto start = std::chrono::steady_clock::now();
    std::vector<std::jthread> threads;
    threads.reserve(ThreadCount);

    for (unsigned workerId = 0; workerId < ThreadCount; ++workerId)
    {
        threads.emplace_back(Worker, std::ref(balances), workerId);
    }
    for (auto& thread : threads)
    {
        thread.join();
    }

    const auto elapsed = std::chrono::steady_clock::now() - start;
    const Money actualTotal = std::accumulate(balances.begin(), balances.end(), Money{0});
    const auto negativeBalances = std::count_if(
        balances.begin(), balances.end(), [](Money balance) { return balance < 0; });

    std::cout << "Expected total: " << expectedTotal << '\n';
    std::cout << "Actual total:   " << actualTotal << '\n';
    std::cout << "Negative accounts: " << negativeBalances << '\n';
    std::cout << "Elapsed: "
              << std::chrono::duration_cast<std::chrono::milliseconds>(elapsed).count()
              << " ms\n";

    return (actualTotal == expectedTotal && negativeBalances == 0) ? 0 : 1;
}
```

#### Что требуется сделать

**3. Реализовать блокировки отдельных счетов — 20 баллов**

Измените программу так, чтобы каждый банковский счёт имел собственный мьютекс.

Переводы между счетами, не имеющими общих участников, должны иметь возможность выполняться параллельно.

Обеспечьте отсутствие взаимных блокировок (*deadlock*), в том числе при одновременных переводах A → B и B → A.

### Задание 2 — Многопоточная поисковая система по текстовым документам — **200 баллов**

На основе предоставленной заготовки разработайте многопоточную поисковую систему,
которая индексирует текстовые файлы на диске и выполняет поиск документов по словам.

Вам предоставлена [**работающая однопоточная программа**](search_engine_project/search_engine_starter.cpp),
содержащая два основных класса:

- `DocumentDb` — хранит документы в памяти и выполняет поиск.
- `UserInterface` — обеспечивает взаимодействие с пользователем через консоль.

В заготовке уже реализованы:

- добавление текстового файла в базу данных;
- хранение документов и их идентификаторов;
- поиск документов по текстовому запросу;
- простое ранжирование по количеству найденных слов запроса;
- интерактивный интерфейс командной строки.

Однако программа имеет ряд ограничений:

- `DocumentDb` не является потокобезопасным;
- поиск выполняется по подстрокам, а не по отдельным словам;
- отсутствует параллельная индексация файлов;
- нельзя добавлять целые каталоги;
- нельзя удалять документы из базы.

Ваша задача — устранить эти ограничения и обеспечить корректную работу программы
при одновременном выполнении нескольких операций.

**Основная цель задания** — научиться организовывать безопасный доступ к разделяемым данным,
выполнять длительные операции параллельно и минимизировать время удержания блокировок.

#### Требования к окружению

- Язык реализации: **C++20**.
- ОС: Linux/macOS/Windows.
- Разрешается использовать стандартную библиотеку C++ и готовые реализации пула потоков, например `boost::asio::thread_pool`.
- Также можно использовать собственный `ThreadPool`, разработанный в другом задании лабораторной работы.
- База документов хранится **в памяти процесса**. Сохранять её между запусками не требуется.
- Использовать готовые библиотеки полнотекстового поиска запрещается.

Разрешается изменять архитектуру предоставленной программы, выделять
дополнительные классы и разделять исходный код на несколько файлов.

---

#### Формат запуска и режим работы

После запуска программа переходит в интерактивный режим (REPL, Read-Evaluate-Print Loop).

Она считывает команды из `stdin` и печатает результаты в `stdout`.

Каждая команда вводится на отдельной строке. Пустые строки игнорируются.

Программа должна поддерживать выполнение фоновых операций индексирования.
Во время индексирования каталога пользователь должен иметь возможность выполнять поисковые запросы и другие команды.

#### Поддерживаемые команды

##### 1. Добавление файла в индекс

```text
add_file PATH
```

Добавляет текстовый файл по пути `PATH`.

Если документ с таким путём уже существует в базе, его содержимое обновляется.
При повторном добавлении идентификатор документа должен сохраняться.

**Метаданные документа (минимум):**

- `id` — уникальное 64-битное целое число;
- `path` — абсолютный или нормализованный путь к файлу;
- содержимое документа либо информация о содержащихся в нём словах.

Разрешается сохранить структуру хранения из заготовки:

```cpp
struct Document
{
    DocumentId id;
    std::filesystem::path path;
    std::vector<std::string> lines;
};
```

При добавлении файла его содержимое следует сначала прочитать и обработать, а затем опубликовать в общей базе документов.

Другие потоки не должны наблюдать документ в частично обновлённом состоянии.

Команда `add_file` может выполняться синхронно.

Для сравнения путей рекомендуется использовать единый способ нормализации, например `std::filesystem::absolute()` и `lexically_normal()`.

##### 2. Добавление файлов из каталога

```text
add_dir PATH
```

Индексирует **все обычные файлы верхнего уровня** каталога `PATH` без обхода подкаталогов.

Индексирование разных файлов выполняется параллельно.

Для распределения задач между рабочими потоками используйте пул потоков с ограниченным количеством рабочих потоков.

Создавать отдельный системный поток для каждого файла запрещается.

**Команда не должна ожидать завершения индексирования всех файлов.**

После запуска фоновой индексации программа должна продолжать обрабатывать другие команды.

Пример:

```text
> add_dir ./documents
Indexing started

> find linux kernel
Search took 0.0021s:
1. id:1, relevance:2.00, path:./documents/linux.txt

> wait
Indexing completed
```

Во время фонового индексирования поиск должен работать с уже добавленными документами.

Файлы, обработка которых ещё не завершена, могут отсутствовать в результатах поиска.

Для упрощения реализации разрешается перечислять файлы каталога в потоке обработки команд,
а их чтение и добавление выполнять в рабочих потоках.

##### 3. Поиск документов

```text
find QUERY
```

Ищет документы, содержащие хотя бы одно слово из запроса.

Поиск должен выполняться без учёта регистра английских букв.

Документы сортируются по убыванию релевантности. Выводится не более 10 документов.

Документы с нулевой релевантностью не должны включаться в результаты.

**В основной части задания используйте простую модель ранжирования:**

- за каждое различное слово запроса, присутствующее в документе, начисляется 1 балл;
- если слово встречается в документе несколько раз, оно всё равно даёт только 1 балл;
- повторяющиеся слова в запросе учитываются один раз.

Например, для запроса:

```text
find linux kernel mode
```

Документ, содержащий слова `linux` и `kernel`, получает 2 балла.

Документ, содержащий только `mode`, получает 1 балл.

Документ, содержащий все три слова, получает 3 балла.

При равной релевантности документы должны сортироваться по возрастанию `id`, чтобы результат был воспроизводимым.

**Реализовывать TF-IDF в основной части задания не требуется.**

Для измерения времени поиска рекомендуется использовать `std::chrono::steady_clock`.

##### 4. Пакетный поиск

```text
find_batch PATH
```

Выполняет поисковые запросы из текстового файла `PATH`.

Каждая непустая строка файла содержит отдельный запрос.

Запросы должны обрабатываться параллельно, например с помощью пула потоков.

Для каждого запроса выведите его порядковый номер, текст запроса и найденные документы.

Пример:

```text
> find_batch ./queries.txt

2. query: linux kernel
   Search took 0.0031s:
   1. id:4, relevance:2.00, path:./docs/linux.txt
   2. id:7, relevance:1.00, path:./docs/kernel.txt
---

1. query: operating systems
   Search took 0.0025s:
   1. id:3, relevance:2.00, path:./docs/os.txt
---
```

Порядок вывода результатов отдельных запросов может отличаться от порядка строк во входном файле,
поскольку запросы выполняются параллельно.

Однако строки результата одного запроса не должны перемешиваться со строками результатов других запросов.

Команда может завершаться после выполнения всех запросов из файла.

##### 5. Удаление файла из индекса

```text
remove_file PATH
```

Удаляет документ по указанному пути из базы.

Сам файл на диске **не удаляется**.

Если документа с таким путём нет в базе, операция ничего не изменяет.

Повторное добавление ранее удалённого документа создаёт запись с новым идентификатором.

##### 6. Удаление документов каталога

```text
remove_dir PATH
```

Удаляет из базы все документы, расположенные непосредственно в указанном каталоге, без рекурсии.

Файлы на диске не удаляются.

Рекомендуется определять принадлежность документа каталогу по сохранённому нормализованному пути,
не перечитывая содержимое каталога с диска.

Удаление должно корректно работать при одновременном выполнении поисковых запросов.

Команда может выполняться синхронно.

##### 7. Ожидание завершения фоновой индексации

```text
wait
```

Ожидает завершения всех фоновых операций индексирования, запущенных до вызова команды.

Например:

```text
> add_dir ./documents
Indexing started

> wait
Indexing completed

> find linux
...
```

После возвращения из `wait` все успешно обработанные соответствующими задачами файлы должны находиться в базе,
если они не были впоследствии удалены или обновлены другой операцией.

Если при индексировании отдельных файлов возникли ошибки, программа должна сообщить о них.

##### 8. Завершение программы

```text
exit
```

или

```text
quit
```

При завершении программа должна корректно остановить рабочие потоки и освободить ресурсы.

Нельзя уничтожать `DocumentDb`, пока фоновые задачи продолжают обращаться к нему.

Рекомендуется дождаться выполнения всех принятых задач перед завершением приложения.

#### Что считается словом и как разбирать текст

В предоставленной заготовке поиск реализован упрощённо: запрос разбивается по пробельным символам,
а затем используется `std::string::find()`.

Например, запрос:

```text
art
```

может найти документ, содержащий слово:

```text
start
```

Это поведение необходимо исправить.

В основной части задания используйте следующие правила:

- **Слово** — последовательность из одного или нескольких символов английского алфавита `[A-Za-z]+`.
- Всё, что не входит в `[A-Za-z]`, является разделителем слов.
- Регистр английских букв игнорируется.
- Правила выделения слов из документа и поискового запроса должны быть одинаковыми.

Например, строка:

```text
Hello, world! Linux-based OS version 2.0
```

должна разбиваться на слова:

```text
hello
world
linux
based
os
version
```

Слово `art` больше не должно совпадать со словом `start`.

Можно использовать `std::regex`, написать собственный разбор строки или воспользоваться другими средствами стандартной библиотеки.

**Поддержка Unicode и корректное выделение русских слов в основной части задания не требуются.**

Предполагается, что текстовые файлы имеют кодировку UTF-8. Неанглийские символы рассматриваются как разделители.

Пустые файлы допускаются. Если запрос не содержит ни одного допустимого слова,
программа должна сообщить об ошибке пустого запроса.

#### Параллелизм и синхронизация

Класс `DocumentDb` должен быть **потокобезопасным**.

Он должен поддерживать одновременные обращения из нескольких системных потоков.

В частности:

1. Несколько потоков могут одновременно выполнять поиск документов.
2. Разные потоки могут одновременно читать и обрабатывать файлы для последующего добавления.
3. Поиск может выполняться во время фонового индексирования.
4. Удаление и обновление документов не должны приводить к гонкам данных.
5. Другие потоки не должны наблюдать частично добавленные или частично обновлённые документы.

Для синхронизации используйте стандартные примитивы C++:

- `std::mutex`;
- `std::shared_mutex`;
- `std::lock_guard`;
- `std::unique_lock`;
- `std::shared_lock`;
- другие примитивы при необходимости.

**Обратите внимание:** поисковые запросы не изменяют базу документов.

Подумайте, как организовать синхронизацию, чтобы несколько операций чтения могли выполняться одновременно.

Рекомендуется рассмотреть `std::shared_mutex`,
позволяющий нескольким потокам одновременно владеть разделяемой блокировкой,
но требующий эксклюзивной блокировки для изменения данных.

##### Продолжительность критических секций

Не следует удерживать эксклюзивную блокировку базы документов во время длительного чтения файла с диска.

Рекомендуемый подход:

1. Прочитать файл и подготовить его содержимое в локальных данных рабочего потока.
2. Захватить блокировку для изменения базы.
3. Добавить или обновить документ.
4. Освободить блокировку.

Это позволяет другим потокам продолжать поиск, пока выполняется чтение файлов.

При поиске разрешается удерживать разделяемую блокировку на время обращения к внутренним данным базы.
Альтернативно можно использовать неизменяемые снимки данных.

##### Согласованность состояния

При одновременном индексировании одного и того же файла в базе
не должно появляться несколько записей с одинаковым нормализованным путём.

Каждая операция изменения базы должна оставлять её в корректном состоянии.

Если несколько операций изменения одного документа перекрываются по времени,
итоговое состояние должно соответствовать некоторому последовательному порядку их выполнения.

Если удаление документа происходит одновременно с его фоновой индексацией,
документ может появиться в базе снова, если операция добавления завершится после удаления.
Такое поведение допускается.

Результаты поиска должны содержать собственные данные результата, а не ссылки на внутренние объекты,
которые могут быть удалены другим потоком.

#### Организация пула потоков

Для параллельной обработки файлов используйте ограниченное количество рабочих потоков.

Можно:

- применить собственный `ThreadPool`;
- воспользоваться `boost::asio::thread_pool`;
- разработать другой механизм на основе стандартных потоков.

Не допускается создавать по отдельному системному потоку на каждый индексируемый файл.

Количество рабочих потоков должно задаваться или определяться при запуске программы.

Можно использовать `std::thread::hardware_concurrency()` как ориентир, учитывая, что функция может вернуть 0.

Рабочие потоки не должны постоянно опрашивать очередь задач в цикле с `sleep_for()`.

При отсутствии задач они должны ожидать поступления работы с использованием соответствующих примитивов синхронизации.

#### Бонус: ранжирование по TF-IDF — **+50 баллов**

Реализуйте более точную модель оценки релевантности документов
на основе **TF-IDF** (*Term Frequency — Inverse Document Frequency*).

В отличие от простого подсчёта найденных слов, TF-IDF учитывает:

- насколько часто слово встречается в конкретном документе;
- насколько редко слово встречается во всей коллекции документов.

Редкие слова, характерные для небольшого числа документов, обычно позволяют лучше отличать релевантные документы от остальных.

##### Теория: Term Frequency (TF)

TF показывает относительную частоту слова в конкретном документе.

Используйте формулу:

\[
TF(t,d)=\frac{count(t,d)}{wordsCount(d)}
\]

где:

- `t` — слово;
- `d` — документ;
- `count(t,d)` — количество вхождений слова `t` в документ `d`;
- `wordsCount(d)` — общее количество слов в документе `d`.

Например, документ содержит текст:

```text
linux kernel linux system
```

В документе 4 слова, из которых `linux` встречается 2 раза.

Следовательно:

\[
TF(\text{linux},d)=\frac{2}{4}=0.5
\]

##### Теория: Inverse Document Frequency (IDF)

IDF оценивает, насколько редким является слово во всей коллекции документов.

Используйте формулу:

\[
IDF(t)=\ln\left(\frac{N}{df(t)}\right)
\]

где:

- `N` — общее количество индексированных документов;
- `df(t)` — количество документов, содержащих слово `t`;
- `ln` — натуральный логарифм.

Если слово присутствует во всех документах, его IDF равен нулю:

\[
IDF(t)=\ln(1)=0
\]

Такое слово не помогает различать документы по релевантности.

Если слово встречается только в одном документе большой коллекции, его IDF будет выше.

##### Теория: оценка релевантности

TF-IDF отдельного слова:

\[
TFIDF(t,d)=TF(t,d)\cdot IDF(t)
\]

Релевантность документа запросу вычисляется как сумма TF-IDF для различных слов запроса:

\[
score(d,q)=\sum_{t\in unique(q)} TF(t,d)\cdot IDF(t)
\]

Слова, отсутствующие в документе, дают нулевой вклад.

##### Пример расчёта

Пусть в базе находятся три документа:

| Документ | Текст |
|---|---|
| `a.txt` | `a cat is an animal` |
| `b.txt` | `a dog is an animal too` |
| `c.txt` | `a sparrow is a bird` |

Выполним запрос:

```text
find a cat
```

**Шаг 1. Вычислим IDF.**

Слово `a` встречается во всех трёх документах:

\[
IDF(a)=\ln(3/3)=0
\]

Слово `cat` встречается только в одном документе:

\[
IDF(cat)=\ln(3/1)\approx1.09861
\]

**Шаг 2. Вычислим TF.**

| Документ | TF(`a`) | TF(`cat`) |
|---|---:|---:|
| `a.txt` | 1/5 = 0.2 | 1/5 = 0.2 |
| `b.txt` | 1/6 ≈ 0.16667 | 0 |
| `c.txt` | 2/5 = 0.4 | 0 |

**Шаг 3. Вычислим релевантность.**

Для `a.txt`:

\[
score(a.txt)=0.2\cdot0+0.2\cdot1.09861\approx0.21972
\]

Для `b.txt` и `c.txt` релевантность равна нулю.

Итог:

| Документ | Релевантность |
|---|---:|
| `a.txt` | 0.21972 |
| `b.txt` | 0 |
| `c.txt` | 0 |

В результаты поиска попадёт только `a.txt`.

Обратите внимание: слово `a` не влияет на ранжирование, поскольку встречается во всех документах.

##### Требования к реализации TF-IDF

1. Используйте формулы TF и IDF, приведённые выше, без дополнительного сглаживания.
2. При вычислении TF учитывайте количество вхождений слова в документ.
3. При вычислении IDF учитывайте общее количество документов и количество документов, содержащих слово.
4. Повторяющиеся слова поискового запроса учитывайте один раз.
5. Документы с нулевой релевантностью не включайте в результаты.
6. При равной релевантности сортируйте документы по возрастанию `id`.
7. При добавлении, обновлении и удалении документов результаты TF-IDF должны корректно изменяться.

Для пустой базы возвращайте пустой результат. Слова, которые отсутствуют во всей коллекции (`df(t) == 0`),
пропускайте, не вычисляя логарифм.

**Особое внимание уделите потокобезопасности.**

TF-IDF использует общие статистические данные всей коллекции.
Поисковый запрос должен вычислять оценки на основе согласованного состояния базы.

Нельзя, например, взять общее число документов из одного состояния базы,
а частоты слов — из другого, если за это время другие потоки изменили коллекцию.

Реализовывать инвертированный индекс для этого бонуса необязательно.

TF-IDF можно вычислять и последовательным перебором документов, хотя это будет менее эффективно.

Для вычисления логарифма можно использовать `std::log()` из стандартной библиотеки C++.

#### Бонус: инвертированный индекс — **+40 баллов**

Оптимизируйте поиск документов, реализовав **инвертированный индекс** (*inverted index*).

В основной части задания разрешается использовать последовательный перебор всех документов,
проверяя наличие слов поискового запроса.

Однако при увеличении количества документов такой поиск становится всё более затратным:
даже если искомое слово встречается только в нескольких документах, программе приходится просматривать всю коллекцию.

Инвертированный индекс позволяет ускорить поиск, сохраняя для каждого слова информацию о документах, в которых оно встречается.

##### Принцип работы

Допустим, в базе находятся три документа:

| Документ | Содержимое |
|---|---|
| `1.txt` | `linux kernel system` |
| `2.txt` | `linux threads` |
| `3.txt` | `windows system threads` |

Инвертированный индекс может выглядеть следующим образом:

```text
linux   → [1, 2]
kernel  → [1]
system  → [1, 3]
threads → [2, 3]
windows → [3]
```

Здесь каждому слову соответствует список идентификаторов документов, содержащих это слово.

Например, при запросе:

```text
find linux threads
```

поисковая система получает:

```text
linux   → [1, 2]
threads → [2, 3]
```

После этого можно определить релевантность документов, не перебирая всю коллекцию:

| Документ | Найденные слова | Релевантность |
|---|---|---:|
| `2.txt` | linux, threads | 2 |
| `1.txt` | linux | 1 |
| `3.txt` | threads | 1 |

##### Требования к реализации

1. Реализуйте структуру данных, сопоставляющую каждому слову идентификаторы документов, в которых оно встречается.

2. При добавлении документа индекс должен пополняться информацией о его словах.

3. При обновлении существующего документа информация о его старом содержимом должна удаляться из индекса
   и заменяться новой. Идентификатор документа при этом сохраняется.

4. При удалении документа все ссылки на него должны удаляться из инвертированного индекса.

5. Метод `FindDocuments()` должен использовать инвертированный индекс для определения подходящих документов,
   **не перебирая все документы базы**.

6. Результаты поиска и порядок ранжирования должны соответствовать требованиям основной части задания.

7. Инвертированный индекс должен корректно работать при одновременном выполнении поиска,
   добавления, обновления и удаления документов из нескольких потоков.

8. Изменение документа и соответствующее изменение индекса должны выполняться согласованно:
   другие потоки не должны наблюдать частично обновлённый индекс.

9. Индекс должен обновляться инкрементально. Перестраивать весь индекс при каждом добавлении или удалении документа не допускается.

##### Подсказки по реализации

Для хранения индекса можно использовать:

```cpp
std::unordered_map<
    std::string,
    std::unordered_set<DocumentId>
> invertedIndex;
```

Для каждого слова здесь хранится множество документов, содержащих его.

Если вы также планируете реализовать бонус с TF-IDF, полезно сохранять количество вхождений каждого слова в документ:

```cpp
std::unordered_map<
    std::string,
    std::unordered_map<DocumentId, size_t>
> invertedIndex;
```

В таком случае значение `size_t` обозначает частоту слова в конкретном документе.

Это позволит использовать одну структуру данных как для поиска, так и для вычисления TF-IDF.

Для эффективного удаления и обновления документов рекомендуется также хранить информацию о словах каждого документа.

Выбор конкретных контейнеров и организация синхронизации остаются на ваше усмотрение.

### Задание 4 — Потокобезопасная очередь — **100 баллов**

Спроектировать и реализовать потокобезопасную ограничиваемую очередь `ThreadSafeQueue<T>`,
поддерживающую безопасную работу из нескольких потоков производителей и потребителей.
Очередь должна корректно работать как в ограниченном (bounded), так и в неограниченном (unbounded) режимах.

#### Окружение

- Язык: **C++20**
- ОС: Linux/macOS/Windows
- Разрешено: стандартная библиотека (`<mutex>`, `<condition_variable>`, `<deque>`, `<memory>`, `<optional>` и т. п.).
- Запрещено: готовые очереди из сторонних библиотек (folly, TBB, Boost.Lockfree и т. п.).

#### Требования к API

##### Конструкторы

```cpp
explicit ThreadSafeQueue(size_t capacity = 0);
```

- `capacity == 0` → очередь неограничена.
- `capacity  > 0` → очередь ограничена: операции вставки блокируются при заполнении.

##### Методы

```cpp
// Добавляет в конец, блокируется если очередь полна (только в bounded-режиме).
void Push(const T& value);
void Push(T&& value);

// Не блокируется: возвращает false, если очередь была полна (bounded-режим).
[[nodiscard]] bool TryPush(const T& value);
[[nodiscard]] bool TryPush(T&& value);

// Пытается изъять: false / nullptr, если пусто
bool TryPop(T& out);
std::unique_ptr<T> TryPop();

// Ждёт появления элемента и возвращает его по значению.
// Определён только если T — nothrow_move_constructible.
T WaitAndPop();  // Используйте SFINAE или static_assert для ограничения

// Ждёт появления элемента, записывает в out.
void WaitAndPop(T& out);

// Информация о состоянии.
size_t GetSize() const;
bool   IsEmpty() const;

// Потокобезопасный обмен содержимым.
void Swap(ThreadSafeQueue& other);
void Swap(std::deque<T>& other); // обменивает внутренний буфер со внешней deque
```

##### Поведение

- **Многопоточность**: Любое количество производителей и потребителей. Отсутствие дедлоков и «проглоченных» уведомлений.
  Корректная работа при **ложных пробуждениях**.
- **Ограниченная очередь**:
  - `Push` — **блокируется**, пока не освободится место.
  - `TryPush` — **не блокируется**, возвращает `false`, если нет места.
- **Неограниченная очередь**:
  - `Push` и `TryPush` всегда вставляют (если не произошло исключение из-за копирования/перемещения `T`).
- **Исключения**:
  - Минимум — **базовая гарантия** (invariants сохранены, утечек нет).
- **Сложность**: амортизированно `O(1)` на `Push/TryPush/TryPop/WaitAndPop`.

##### Подсказки по реализации

- Контейнер хранения: `std::deque<T>`.
- Синхронизация: один `std::shared_mutex` + две `std::condition_variable`:
  - `cv_not_empty` — для ожидания элемента,
  - `cv_not_full`  — для ожидания места (в bounded-режиме).
- **Порядок блокировок при Swap** двух очередей:
  - Используйте `std::scoped_lock lk(mtx_a, mtx_b);` (или **адресный порядок** для C++17), чтобы исключить дедлок.
- `Swap(std::deque<T>& other)`: блокируйте `this->mtx`, затем `std::swap(buffer_, other)`, затем сингналите обе CV при необходимости.
- Не забывайте о **ложных пробуждениях**: `wait` всегда с предикатом или в цикле.
- `GetSize()` можно делать под мьютексом либо поддерживать атомарный счётчик.

#### Гарантии корректности и исключений

- **Базовая гарантия** для всех методов: invariants класса сохраняются; при исключениях состояние очереди валидно.
- `WaitAndPop()` по значению — разрешён **только**, если `T` — `std::is_nothrow_move_constructible_v<T> == true`.
- Иначе — ошибка ошибка компиляции с внятным сообщением.
- **Отсутствие дедлоков**:
  - Не блокируйте `Push/TryPush` навсегда в unbounded-режиме.
  - В bounded-режиме `Push` должен разблокироваться, когда потребитель извлёк элемент и подал сигнал.

#### Примеры использования

```cpp
ThreadSafeQueue<int> q(2); // bounded на 2 элемента

std::jthread prod([&]{
  for (int i = 0; i < 10; ++i) q.Push(i);
});

std::jthread cons([&]{
  for (int i = 0; i < 10; ++i) {
    int x = q.WaitAndPop();
    // обработка x
  }
});

prod.join();
cons.join();
```

#### Тестирование

##### Обязательные модульные тесты (примерные кейсы)

1. **Базовые операции (single-thread)**

   - `TryPop` на пустой → `false`/`nullptr`.
   - `Push` + `TryPop` возвращает то же значение (копия/перемещение).
   - `GetSize/IsEmpty` корректны.
2. **Bounded семантика**

   - `capacity=1`: второй `TryPush` → `false`.
   - `Push` блокируется, пока другой поток не выполнит `TryPop/WaitAndPop`.
3. **Unbounded семантика**

   - `capacity=0`: последовательные `Push` не блокируются; порядок FIFO сохраняется.
4. **Параллельность MPMC**

   - N производителей, M потребителей; суммарно вставлено K элементов; все K извлечены и без потерь/дубликатов .
5. **Spurious wakeups**

   - Стресс-тест ожиданий (`WaitAndPop`), чтобы убедиться, что предикаты корректны.
6. **Исключения из копирования/перемещения T**

   - Специальный тип-«бомба», бросающий при копировании (или аллокации через счётчик). Очередь остаётся в валидном состоянии.
7. **Swap(ThreadSafeQueue&)**

   - Перестановка содержимого двух очередей (в т. ч. разных `capacity`).
     Нет дедлоков при 2 потоках, одновременно меняющих очереди.
8. **Swap(std::deque\<T\>&)**

   - Буфер обменялся, размеры/пустота корректны, уведомления поданы (после swap можно `Push`/`WaitAndPop`).

### Задание №5 — Примитивы синхронизации для пользовательских потоков — **100 баллов**

В лабораторной работе №3 вы реализовали собственный планировщик кооперативных потоков пользовательского уровня
(*green threads*) на основе `Boost.Context`.

Теперь расширьте разработанный runtime, добавив поддержку **синхронизации между пользовательскими потоками**.

В основной части задания необходимо реализовать аналог мьютекса — `FiberMutex`,
который позволяет пользовательским потокам организовать взаимное исключение при работе с общими данными.

В качестве бонусов предлагается реализовать другие примитивы синхронизации:

- `FiberSemaphore` — семафор;
- `FiberConditionVariable` — условную переменную;
- `FiberBarrier` — барьер;
- `FiberEvent` — событие.

Все примитивы должны работать **на уровне вашего пользовательского планировщика**, 
е блокируя системный поток при ожидании освобождения ресурса.

---

#### Исходные условия

Используйте планировщик из лабораторной работы №3.

Напомним, что он поддерживает:

- создание нескольких пользовательских потоков;
- сохранение и восстановление контекстов с помощью `boost::context::fiber`;
- отдельный стек для каждого пользовательского потока;
- кооперативное переключение между потоками через `Yield()`;
- планирование по алгоритму Round Robin;
- состояния `READY`, `RUNNING`, `FINISHED`.

Все пользовательские потоки должны выполняться в рамках **одного потока операционной системы** (модель N:1).

В каждый момент времени выполняется только один пользовательский поток.

Переключение происходит только тогда, когда выполняющийся поток явно передаёт управление планировщику или завершается.

**Важно:** в такой модели пользовательские потоки не исполняются физически параллельно.
Однако они могут поочерёдно изменять общие данные,
и переключение контекста посреди составной операции может нарушить логические инварианты программы.

Например:

```cpp
int counter = 0;

void Increment()
{
    int value = counter;
    Yield();
    counter = value + 1;
}
```

Если два пользовательских потока выполняют `Increment()`, оба могут прочитать одно и то же значение `counter`,
после чего записать одинаковый результат.

Ваша задача — разработать механизм, позволяющий предотвращать подобные ситуации.

#### Что требуется реализовать

Расширьте ваш runtime следующими возможностями:

1. Перевод пользовательского потока в состояние ожидания.
2. Исключение ожидающих потоков из очереди готовых к выполнению.
3. Пробуждение пользовательского потока по запросу другого потока.
4. Реализация мьютекса `FiberMutex`, использующего эти механизмы.

Ожидание освобождения мьютекса должно выполняться **без активного опроса и без блокировки потока операционной системы**.

#### Расширение состояний пользовательского потока

Добавьте в планировщик состояние `BLOCKED`.

Теперь пользовательский поток может находиться в одном из следующих состояний:

```text
READY
RUNNING
BLOCKED
FINISHED
```

Значение состояний:

| Состояние | Описание |
|---|---|
| `READY` | Поток готов к выполнению и может быть выбран планировщиком |
| `RUNNING` | Поток выполняется в настоящий момент |
| `BLOCKED` | Поток ожидает событие или освобождение ресурса |
| `FINISHED` | Функция пользовательского потока завершилась |

При обычном вызове `Yield()` текущий поток переходит из `RUNNING` в `READY`, поскольку он по-прежнему готов к выполнению.

При блокировании поток переходит из `RUNNING` в `BLOCKED` и **не должен выбираться планировщиком**,
пока другой поток не пробудит его.

При пробуждении заблокированный поток снова переходит в состояние `READY`.

После этого планировщик может выбрать его для выполнения в соответствии с алгоритмом планирования.

Пробуждение не означает, что поток немедленно получает управление.

Если в лабораторной работе №3 вы реализовали бонусные состояния `WAITING` для `Join()` или `SLEEPING` для `Sleep()`,
их можно сохранить. Состояние `BLOCKED` используется для ожидания примитивов синхронизации.

---

#### Блокирование и пробуждение пользовательских потоков

Дополните планировщик механизмами блокирования и пробуждения.

Например, внутренний интерфейс планировщика может включать следующие операции:

```cpp
class Scheduler
{
public:
    // Уже реализованные методы
    void Spawn(/* ... */);
    void Run();
    void Yield();

    // Новые методы
    FiberId CurrentFiber() const;
    void BlockCurrent();
    void Wake(FiberId fiber);
};
```

Приведённый интерфейс является примером. Имена методов, типы и способ организации внутреннего API могут отличаться.

**Операция `BlockCurrent()` должна:**

1. Перевести выполняющийся пользовательский поток в состояние `BLOCKED`.
2. Исключить его из дальнейшего обычного Round Robin планирования.
3. Передать управление планировщику.
4. Приостановить выполнение вызывающей функции до тех пор, пока поток не будет пробуждён.

**Операция `Wake()` должна:**

1. Найти указанный пользовательский поток.
2. Перевести его из `BLOCKED` в `READY`.
3. Добавить поток в очередь готовых к выполнению.

Повторное пробуждение уже готового или завершившегося потока не должно приводить к дублированию записей в очереди
или повторному запуску завершившегося контекста.

Использовать `std::mutex`, `std::condition_variable` или `std::this_thread::sleep_for()` для реализации ожидания
пользовательских потоков запрещено.

**Обратите внимание:** блокирование отличается от `Yield()` тем,
что заблокированный поток не должен автоматически возвращаться в очередь готовых.

#### Реализация `FiberMutex`

Разработайте класс `FiberMutex`, предоставляющий механизм взаимного исключения для пользовательских потоков.

Минимально необходимый интерфейс:

```cpp
class FiberMutex
{
public:
    explicit FiberMutex(Scheduler& scheduler);

    FiberMutex(const FiberMutex&) = delete;
    FiberMutex& operator=(const FiberMutex&) = delete;

    // Записанные в нижнем регистре имена lock и unlock
    // делают ваш мьютекс совместимым со стандартными lock_guard и unique_lock 
    void lock();
    bool try_lock();
    void unlock();

private:
    // Внутреннее состояние мьютекса
};
```

Имена классов могут отличаться.

Мьютекс должен быть связан с тем `Scheduler`, пользовательские потоки которого он синхронизирует.

##### `lock()`

Метод пытается захватить мьютекс.

Если мьютекс свободен, он захватывается текущим пользовательским потоком,
после чего `lock()` возвращает управление вызывающему коду.

Если мьютекс уже захвачен другим пользовательским потоком, вызывающий поток должен:

1. Добавиться в очередь потоков, ожидающих освобождения мьютекса.
2. Перейти в состояние `BLOCKED`.
3. Передать управление планировщику.
4. Продолжить выполнение после получения права владения мьютексом.

После успешного возвращения из `lock()` вызывающий поток должен владеть мьютексом.

##### `try_lock()`

Метод пытается захватить мьютекс без ожидания.

- Если мьютекс свободен — захватывает его и возвращает `true`.
- Если мьютекс занят — возвращает `false`.

При неудачном вызове `try_lock()` пользовательский поток не должен переводиться в состояние `BLOCKED`.

##### `unlock()`

Метод освобождает мьютекс, принадлежащий текущему пользовательскому потоку.

Если ожидающих потоков нет, мьютекс становится свободным.

Если есть ожидающие потоки, один из них должен получить возможность продолжить работу и захватить мьютекс.

Для базовой реализации используйте **FIFO-порядок обслуживания ожидающих потоков**.

Рекомендуется передавать владение мьютексом непосредственно первому ожидающему потоку,
а затем переводить его в состояние `READY`.
В таком случае другой поток не сможет захватить освобождаемый мьютекс раньше уже выбранного ожидающего потока.

##### Дополнительные требования

- Мьютекс может иметь только одного владельца.
- Один пользовательский поток может последовательно захватывать и освобождать мьютекс много раз.
- Повторный вызов `lock()` владельцем без предварительного `unlock()` не поддерживается.
  В отладочной сборке рекомендуется диагностировать такую ошибку.
- `unlock()` разрешается вызывать только владельцу мьютекса.
  Некорректное использование рекомендуется обнаруживать проверкой инвариантов.
- Корректный вызов `unlock()` не должен выбрасывать исключения.
- Поддерживать рекурсивные мьютексы не требуется.
- Завершение пользовательского потока с оставшимся захваченным мьютексом считается ошибкой программы.

#### Совместимость со стандартными RAII-обёртками

Ваш `FiberMutex` должен поддерживать использование:

```cpp
std::lock_guard<FiberMutex>
```

и

```cpp
std::unique_lock<FiberMutex>
```

Например:

```cpp
FiberMutex mutex(scheduler);

void Worker()
{
    std::lock_guard<FiberMutex> lock(mutex);

    // Критическая секция
}
```

Реализовывать собственные аналоги `lock_guard` и `unique_lock` не требуется.

#### Подсказки по реализации

Мьютекс может хранить:

- идентификатор пользовательского потока, владеющего мьютексом;
- очередь идентификаторов потоков, ожидающих его освобождения;
- ссылку на планировщик.

При вызове `lock()` занятый мьютекс добавляет текущий поток в очередь ожидания и блокирует его через планировщик.

При вызове `unlock()` мьютекс выбирает одного ожидающего пользователя и передаёт ему право владения.

В модели N:1 не требуется защищать внутреннее состояние `FiberMutex` с помощью системного мьютекса,
поскольку в каждый момент выполняется только один пользовательский поток.

Однако необходимо внимательно следить за **моментами переключения контекста**.

Например, между проверкой состояния мьютекса и его захватом
не должно происходить переключение на другой пользовательский поток.

Аналогично, постановка потока в очередь ожидания и его блокирование должны быть согласованы между собой.

Не допускайте ситуаций, в которых поток уже исключён из планирования, но информация о необходимости его пробуждения потеряна.

#### Примечание о связи с планировщиком

В лабораторной работе №3 требовалось реализовать `Yield()` без использования глобального указателя на `Scheduler`.

Это требование сохраняется.

Не следует использовать:

```cpp
Scheduler* g_scheduler;
```

для хранения текущего планировщика.

Вместо этого используйте механизм определения текущего пользовательского потока, реализованный ранее.

Например, ваш runtime может хранить в `thread_local` переменной указатель на контекст текущего пользовательского потока,
который, в свою очередь, содержит ссылку на породивший его `Scheduler`.

Каждый `FiberMutex` должен быть связан с конкретным планировщиком.

Применять один `FiberMutex` для синхронизации пользовательских потоков, принадлежащих разным планировщикам, не требуется.

#### Отсутствие готовых потоков

Расширение планировщика состоянием `BLOCKED` создаёт новую ситуацию.

Предположим, что существуют три пользовательских потока:

```text
T1: BLOCKED
T2: BLOCKED
T3: BLOCKED
```

Очередь `READY` пуста, однако ни один пользовательский поток ещё не завершился.

В такой ситуации планировщик не должен считать работу успешно завершённой.

Если все незавершённые потоки заблокированы и отсутствуют другие механизмы,
способные пробудить их, программа находится в состоянии взаимной блокировки (*deadlock*).

Добавьте в планировщик обнаружение такой ситуации.

Достаточно вывести диагностическое сообщение или завершить `Run()` с ошибкой.

Например:

```text
Scheduler error: deadlock detected
```

Если в предыдущей лабораторной был реализован бонусный `Sleep()`,
необходимо учитывать состояние `SLEEPING`: отсутствие готовых потоков не означает deadlock,
если существуют спящие потоки, время пробуждения которых ещё не наступило.

Полноценный алгоритм обнаружения циклов ожидания между произвольными ресурсами реализовывать не требуется.

**1. Захват свободного мьютекса**

**3. Пробуждение ожидающего потока**

После освобождения мьютекса первый ожидающий поток должен стать готовым к выполнению и впоследствии продолжить работу.

#### Бонус: `FiberSemaphore` — **+30 баллов**

Реализуйте считающий семафор для пользовательских потоков.

Пример интерфейса:

```cpp
class FiberSemaphore
{
public:
    FiberSemaphore(Scheduler& scheduler,
                   size_t initialCount);

    void Acquire();
    bool TryAcquire();
    void Release();
};
```

Семафор хранит количество доступных разрешений.

- `Acquire()` получает одно разрешение. Если доступных разрешений нет, текущий пользовательский поток блокируется.
- `TryAcquire()` пытается получить разрешение без блокирования.
- `Release()` освобождает одно разрешение либо передаёт его одному из ожидающих потоков.

В отличие от мьютекса, семафор не привязан к единственному владельцу.
Освобождать разрешение может не тот поток, который его получил.

Реализация не должна использовать системные семафоры.

Для проверки создайте десять пользовательских потоков, которым доступно только три экземпляра некоторого ресурса.

В каждый момент не более трёх пользовательских потоков должны находиться между успешным `Acquire()` и соответствующим `Release()`.

Добавьте явные вызовы `Yield()` внутри участка использования ресурса,
чтобы проверить соблюдение ограничения при переключениях контекста.

#### Бонус: `FiberConditionVariable` — **+50 баллов**

Реализуйте условную переменную для пользовательских потоков.

Пример интерфейса:

```cpp
class FiberConditionVariable
{
public:
    explicit FiberConditionVariable(Scheduler& scheduler);

    void Wait(std::unique_lock<FiberMutex>& lock);

    template <typename Predicate>
    void Wait(std::unique_lock<FiberMutex>& lock,
              Predicate pred);

    void NotifyOne();
    void NotifyAll();
};
```

**Метод `Wait(lock)` должен:**

1. Зарегистрировать текущий пользовательский поток как ожидающий уведомления.
2. Освободить переданный `FiberMutex`.
3. Заблокировать текущий пользовательский поток.
4. После пробуждения повторно захватить мьютекс.
5. Вернуть управление вызывающему коду с захваченным мьютексом.

Регистрация ожидания, освобождение мьютекса и блокирование должны быть организованы так, чтобы уведомление не могло потеряться.

**Метод `Wait(lock, pred)` должен:**

1. Проверить значение предиката `pred()` при захваченном мьютексе.
2. Если предикат возвращает `true`, немедленно завершить ожидание.
3. Если предикат возвращает `false`, вызвать базовый `Wait(lock)`.
4. После пробуждения и повторного захвата мьютекса снова проверить предикат.
5. Повторять ожидание, пока предикат не вернёт `true`.

Предикат должен быть вызываемым объектом, возвращающим значение, приводимое к `bool`.

Реализуйте перегрузку с предикатом через базовую версию `Wait(lock)`, не дублируя механизм блокирования и пробуждения потоков.

`NotifyOne()` пробуждает один ожидающий пользовательский поток, если такой имеется.

`NotifyAll()` пробуждает все ожидающие пользовательские потоки.

Если ожидающих потоков нет, вызов уведомления не должен сохранять уведомление для будущих вызовов `Wait()`.

**Пример использования**

```cpp
FiberMutex mutex(scheduler);
FiberConditionVariable cv(scheduler);

bool ready = false;

// Пользовательский поток-потребитель
auto Consumer = [&]()
{
    std::unique_lock<FiberMutex> lock(mutex);

    cv.Wait(lock, [&] {
        return ready;
    });

    // Условие ready выполнено.
};

// Пользовательский поток-производитель
auto Producer = [&]()
{
    {
        std::lock_guard<FiberMutex> lock(mutex);
        ready = true;
    }

    cv.NotifyOne();
};
```

Для проверки реализуйте задачу Producers/Consumers с общим буфером.

**Требования к тестированию:**

1. Если предикат изначально возвращает `true`, `Wait(lock, pred)` не должен блокировать пользовательский поток.
2. Если предикат возвращает `false`, поток должен блокироваться до получения уведомления и выполнения условия.
3. Если после уведомления предикат по-прежнему возвращает `false`, поток должен повторно перейти в состояние ожидания.
4. Проверьте ситуацию, когда производитель изменил условие и отправил уведомление до вызова `Wait(lock, pred)`.
   Потребитель не должен заблокироваться, если предикат уже возвращает `true`.
5. Проверьте работу `NotifyAll()` при нескольких ожидающих пользовательских потоках.

На защите объясните:

- Почему `Wait(lock, pred)` должен проверять предикат в цикле, а не через `if`?
- Почему предикат необходимо проверять при захваченном мьютексе?
- Чем `Wait(lock, pred)` отличается от `Wait(lock)`?
- Почему уведомление не гарантирует, что ожидаемое условие выполняется?
- Как использование предиката помогает избежать потерянного пробуждения (*lost wakeup*)?

#### Бонус: `FiberBarrier` — **+40 баллов**

Реализуйте барьер для пользовательских потоков.

Барьер предназначен для синхронизации заданного количества участников на определённом этапе выполнения.

Пример интерфейса:

```cpp
class FiberBarrier
{
public:
    FiberBarrier(Scheduler& scheduler,
                 size_t participantCount);

    void ArriveAndWait();
};
```

При вызове `ArriveAndWait()` пользовательский поток сообщает, что достиг барьера.

Если барьера достигли ещё не все участники, текущий поток блокируется.

Когда последний участник достигает барьера, все ожидающие потоки становятся готовыми к выполнению.

Барьер должен поддерживать **многократное использование**.

Например, три пользовательских потока выполняют пять последовательных этапов работы.
Ни один поток не должен переходить к следующему этапу, пока все участники не закончат предыдущий.

При реализации обратите внимание на необходимость различать последовательные поколения (*generations*) барьера.

Протестируйте ситуацию, в которой один поток значительно опережает остальных и быстро доходит до барьера следующего поколения.

Считайте, что число участников фиксировано, каждый участник достигает каждого поколения барьера ровно один раз,
и никто не прекращает участие досрочно. Поддерживать удаление участников и отмену ожидания не требуется.

#### Бонус: `FiberEvent` — **+20 баллов**

Реализуйте объект события для пользовательских потоков.

Пример интерфейса:

```cpp
class FiberEvent
{
public:
    explicit FiberEvent(Scheduler& scheduler);

    void Wait();
    void Set();
    void Reset();
};
```

Используйте семантику *manual-reset event*.

Первоначально событие находится в несигнальном состоянии.

- `Wait()` блокирует текущий пользовательский поток, если событие не установлено.
- `Set()` устанавливает событие и пробуждает все ожидающие потоки.
- Пока событие установлено, последующие вызовы `Wait()` не блокируются.
- `Reset()` возвращает событие в несигнальное состояние.

В отличие от `FiberConditionVariable`, установленное событие сохраняет своё состояние даже при отсутствии ожидающих потоков.

Для проверки создайте несколько пользовательских потоков, ожидающих одно событие. Другой поток должен установить его,
после чего все ожидающие смогут продолжить выполнение.
