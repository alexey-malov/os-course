# game-sim — заготовка лабораторной по планированию потоков Linux

Полная формулировка задания: **[README.md](../README.md)**.

Это **студенческая заготовка**, а не готовое решение. Имитация игровой нагрузки и метрики уже работают.
Реализация функций управления планировщиком в `src/ThreadScheduling.cpp` оставлена студентам.

## Состав проекта

```text
game-sim-lab/
├── CMakeLists.txt
├── README.md
├── src/
│   ├── main.cpp                # запуск и обработка ошибок
│   ├── Simulation.h/.cpp       # CLI, игровые потоки, назначение настроек
│   ├── Workload.h/.cpp         # калиброванная CPU-bound нагрузка
│   ├── Statistics.h/.cpp       # метрики, ограничения, CSV, Game Quality Score
│   └── ThreadScheduling.h/.cpp # TODO: управление pthread + Linux TID
├── scripts/
│   ├── check-starter.sh        # сборка + базовый smoke test
│   └── run-experiments.sh      # demo, baseline, matrix
└── results/                    # результаты появятся после запуска
```

## Сборка (обязательна конфигурация Release)

```bash
cmake -S . -B build/release -DCMAKE_BUILD_TYPE=Release
cmake --build build/release --parallel
ctest --test-dir build/release --output-on-failure
```

Требуются Linux, CMake >=3.20, GCC/Clang с поддержкой C++20 и pthreads.

## Базовый запуск до выполнения TODO

```bash
build/release/game-sim --help
scripts/run-experiments.sh demo
```

Стартовая версия **умеет запускать только базовую конфигурацию** (все потоки `SCHED_OTHER`,
nice 0, без дополнительного разделения CPU).
При запросе реального изменения приоритета, политики или affinity она сообщает `TODO` и завершает работу,
чтобы пользователь не принял необработанную настройку за применённую. `observed=NOT_IMPLEMENTED` тоже ожидаемо,
пока не выполнена вторая функция.

## Ручной запуск эксперимента

```bash
mkdir -p results
ITERS=$(build/release/game-sim --calibrate)

build/release/game-sim \
    --duration 8 --pool-size 2 --iters-per-ms "$ITERS" \
    --frame-work-ms 9 --ai-work-ms 12 \
    --summary-csv results/demo.csv \
    --events-csv results/demo-events.csv
```

`--pool-size 2` выбирает первые два CPU из **разрешённой процессу affinity-маски** (не обязательно Linux CPU 0 и 1).
Программа ограничивает общий пул CPU в главном потоке **до создания рабочих потоков**; все они наследуют эту маску.
Эту инфраструктурную операцию студент не реализует — его задача настроить **каждый поток отдельно**.

`--placement shared` оставляет весь пул доступным всем потокам.
`--placement split` закрепляет Audio/Frame за первым CPU, AI/Asset за вторым.
Его можно заменить или уточнить индивидуальными масками по **индексам в пуле**:

```bash
# После выполнения TODO, pool-size=2:
# Audio и Frame -> первый выбранный CPU;
# AI -> второй; Asset -> оба CPU.
build/release/game-sim \
    --pool-size 2 --placement split \
    --asset-cpu-indices 0,1 \
    --ai-nice 5 --asset-nice 10
```

Команды с изменением параметров работают после выполнения TODO студентом.

## Скрипт для серий экспериментов

```bash
scripts/run-experiments.sh demo
scripts/run-experiments.sh baseline A
REPEATS=3 scripts/run-experiments.sh matrix
```

- `demo`: быстрый двухсекундный запуск базового случая на одном CPU. Работает в исходной заготовке.
- `baseline A`: базовая конфигурация сцены A (или B, C, D).
- `matrix`: четыре сцены × три конфигурации (`baseline`, `weighted`, `split`), по `REPEATS` повторений. Работает **после** реализации управления параметрами.

Параметры через переменные среды: `DURATION` (по умолчанию 8 с),
`POOL_SIZE` (по умолчанию 2, `split` требует 2),
`ASSET_THREADS` (по умолчанию 4), `REPEATS` (по умолчанию 1),
`ITERS_PER_MS` (необязательное постоянное значение калибровки),
`RESULTS` (каталог отчётов).

Скрипт сохраняет первую калибровку в `results/iterations-per-ms.txt` и использует её повторно.
Если нужно начать измерения с другой калибровкой, удалите файл **до всей серии**, но не между сравниваемыми запусками.

Результаты сохраняются в `<scene>-<profile>-<repeat>.csv`, `<...>-events.csv`, `<...>.log`.
Скрипт автоматически передаёт измеренную производительность Asset из базовой конфигурации
в альтернативные конфигурации **того же сценария и повтора**.
В файле baseline нормализованный показатель Asset отсутствует, потому что внешняя опорная производительность ещё не задана.

## Как понимать статистику

- **Response Time:** от запланированного момента поступления работы до завершения, включая ожидание CPU.
- **P99 Response:** 99-й процентиль среди завершённых работ.
- **Missed:** завершения после дедлайна **и** пропущенные задания; знаменатель — число всех запланированных заданий.
- **P99 Wake:** 99-й процентиль задержки между запланированным запуском и началом обработки.
- **Avg-CPU:** фактическое процессорное время выполнения вычислений, а не время ожидания.
- **Asset Throughput:** количество подготовленных условных ресурсов в секунду за общий интервал измерения.
- **Quality Score:** учебная функция 0–100 на основе запаса до дедлайна;
  она сама по себе **не подтверждает** выполнение требований.
- **ACCEPTABILITY:** `PASS`/`FAIL` только при наличии `--asset-baseline-rate`. Иначе `BASELINE_REQUIRED`.

Целевые `--*-work-ms` определяют количество итераций относительно калибровки; это **приблизительное CPU-время**,
не гарантированный WCET (Worst-Case Execution Time).
Стандартный планировщик Linux может показывать хорошие результаты без ручной настройки, что является допустимым выводом.

## Технические подсказки

- `thread.native_handle()` даёт pthread-дескриптор для `pthread_setschedparam()`
  и `pthread_setaffinity_np()` в используемой Linux-среде.
- Для `setpriority(PRIO_PROCESS, tid, nice)` используйте **Linux TID**,
  опубликованный рабочим потоком. Не передавайте туда `pthread_t`.
- POSIX-функции `pthread_*` возвращают **код ошибки непосредственно**.
  `setpriority()` и `getpriority()` используют `errno`.
- Для обычных политик (`SCHED_OTHER`, `SCHED_BATCH`, `SCHED_IDLE`) `sched_priority` обязан быть 0.
- При `SCHED_IDLE` nice не влияет на распределение CPU.
- Все рабочие потоки ожидают общего разрешения старта до завершения настройки.
- В `src/ThreadScheduling.cpp` находятся обе основные заготовки с пометками TODO.

## Почему проект не запускается с `--asset-nice 10`, а требует доработки?

Это намеренно. В заготовке студент должен реализовать `ApplyThreadSettings()` и `ReadThreadSettings()`.
До этого при попытке изменить настройки выводится сообщение `TODO`,
а не создаётся иллюзия, что новые значения действительно применены.
