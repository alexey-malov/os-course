### Задание 1 — `scheduler-tools`: исследование планировщика Linux

**Максимум: 100 баллов.** Задание состоит из трёх независимо оцениваемых серий: масштабирование (40 баллов),
приоритеты (30 баллов) и отзывчивость (30 баллов).

#### Цель работы

Научиться использовать инструменты командной строки Linux для наблюдения и настройки планирования системных потоков;
экспериментально исследовать влияние числа потоков, CPU Affinity,
относительного приоритета и политики планирования на CPU-bound и I/O-bound приложения.

В этой работе **не требуется писать собственные нагрузочные программы или изменять их алгоритмы**:
исходные коды и сценарии запуска предоставляются.
Основная работа состоит в подготовке экспериментов, сборе измерений и объяснении результатов.

#### Предоставленные программы и инструменты

В [комплект](scheduler-tools-lab/) включены три самостоятельных CMake-проекта, а также общий CMake-проект для одновременной сборки:

| Программа | Характер нагрузки | Принцип работы |
|---|---|---|
| `cpu-local` | CPU-bound, независимые потоки | Каждый поток меняет собственную локальную `volatile`-переменную; общий объём итераций делится между потоками. |
| `cpu-shared` | CPU-bound, взаимодействующие потоки | Все потоки обновляют **один** `std::atomic<uint64_t>` через `fetch_add(..., memory_order_relaxed)`. |
| `io-pipe` | I/O-bound | Отдельный Producer посылает сообщения через pipe, а Consumer блокируется на чтении и измеряет задержки доставки и пробуждения. |

**Программы специально упрощены.** `volatile` используется только для сохранения операций с локальной переменной
и **не является** способом синхронизации потоков.
В `cpu-shared` используется атомарное обновление общего счётчика,
чтобы проявилась конкуренция за кэш-линию.
В режиме фиксированного числа итераций внутри вычислительных циклов не выполняются системные вызовы.

Исследуемые инструменты: `taskset`, `nice`, `renice`, `chrt`, `ps -L`, `top -H`, `/usr/bin/time` (при наличии). 
ри выполнении задания **не использовать `sudo` и политики `SCHED_FIFO` / `SCHED_RR`**:
для требуемых экспериментов достаточно политик `SCHED_OTHER`, `SCHED_BATCH` и `SCHED_IDLE`.

#### Подготовка среды

##### 1. Соберите программы в Release-конфигурации

В корне распакованного проекта выполните:

```bash
cmake -S . -B build/release -DCMAKE_BUILD_TYPE=Release
cmake --build build/release --parallel
```

После сборки исполняемые файлы находятся в `build/release/bin/`.

**Обязательное требование: все измерения производительности выполняются только в Release-конфигурации.**
Не сравнивайте Debug- и Release-сборки, не меняйте флаги компиляции между сравниваемыми запусками.
Изменение числа потоков или ограничений affinity не должно изменять общий объём полезной работы программы.

Каждый подкаталог (`cpu-local/`, `cpu-shared/`, `io-pipe/`) можно также собрать как отдельный CMake-проект.
Параметры и формат вывода описаны в `README.md` и в справке `--help`.

##### 2. Выясните доступные CPU

```bash
grep Cpus_allowed_list /proc/self/status
taskset -pc $$
lscpu
```

Выберите два **разрешённых** логических CPU и обозначьте их `CPU_A` и `CPU_B`. Например, если разрешены CPU 2 и 3:

```bash
CPU_A=2
CPU_B=3
```

**Не предполагайте, что CPU 0 обязательно доступен**: контейнер или учебная среда могут ограничивать допустимый набор.
Если доступны четыре CPU, для некоторых экспериментов можно использовать четыре.
Если доступны только один или два CPU, сократите матрицу измерений и укажите это ограничение в отчёте.

Если программа запущена через `taskset`, созданные ею системные потоки наследуют заданную маску affinity.
Для наблюдения отдельных потоков используйте `ps -L` или `top -H`.

##### 3. Правила измерений

- Для каждой конфигурации выполните **не менее трёх запусков** и используйте медиану времени либо представьте все три измерения.
- Фиксируйте версию ядра (`uname -r`), доступные CPU, ограничения среды (если есть cgroups/контейнер),
  число потоков и параметры запуска.
- Сравнивайте конфигурации при **одинаковом общем объёме работы**.
- Для `cpu-local` и `cpu-shared` можно выбрать **разные** значения `--iterations`,
  но внутри серии каждого приложения они должны оставаться постоянными.
- Подберите число итераций так, чтобы измерения не сводились к нескольким миллисекундам.
  Во время тестов по возможности закройте тяжёлые фоновые приложения.
- Проверяйте контрольные суммы: у обеих CPU-bound программ `checksum` должен совпадать с запрошенным числом итераций.
- Используйте вывод `elapsed_ms` (настенное время) и `process_cpu_ms` (суммарное процессорное время процесса).
  Это разные метрики.
- Не считайте небольшие флуктуации или отсутствие ожидаемого улучшения ошибкой:
  важны корректность измерения и объяснение причин.

#### Серия B. Приоритеты `nice` и `renice` — **30 баллов**

##### Эксперимент B1. Изменяет ли `nice` скорость работы без конкуренции?

На **одном и том же** CPU запустите однопоточную `cpu-local` с `nice = 0` и `nice = 10`,
не создавая конкурирующих вычислительных процессов:

```bash
taskset -c "$CPU_A" build/release/bin/cpu-local \
    --threads 1 --iterations 1000000000

nice -n 10 taskset -c "$CPU_A" build/release/bin/cpu-local \
    --threads 1 --iterations 1000000000
```

Сравните время завершения и объясните полученный результат.

##### Эксперимент B2. Приоритеты при конкуренции

Запустите на том же CPU независимую длительную вычислительную задачу:

```bash
taskset -c "$CPU_A" build/release/bin/cpu-local \
    --threads 1 --duration-ms 30000 &
HOG_PID=$!
```

Пока конкурент работает, повторите измерения `nice = 0` и `nice = 10` для исследуемой программы с одинаковым `--iterations`.
После эксперимента завершите конкурента:

```bash
kill "$HOG_PID" 2>/dev/null || true
wait "$HOG_PID" 2>/dev/null || true
```

Длительность фоновой задачи должна **превышать время измеряемого запуска**.
Если она завершилась раньше, результат требует повторного измерения.
Запускайте конкурирующие программы из одной терминальной сессии:
в Linux распределение CPU может дополнительно зависеть от autogroup и cgroups.

##### Эксперимент B3. Изменение `nice` во время работы

Запустите два длительных экземпляра `cpu-local` на одном CPU.
Через `ps -L -p PID -o pid,tid,ni,cls,psr,pcpu,comm` определите **TID рабочего потока** одного из процессов
(он обычно отличается от PID главного потока). Измените его nice:

```bash
renice -n 10 -p TID
```

Здесь `TID` заменяется реальным числовым идентификатором.
В Linux nice — атрибут **отдельного потока**,
поэтому команда `renice` только для PID главного потока многопоточного процесса может
не изменить приоритет выполняющего вычисления рабочего потока.
Проверьте изменение через `ps -L` или `top -H` и опишите наблюдения.
Для изменения `nice` в сторону меньшего числа могут потребоваться дополнительные права;
выполнять это необязательно.

##### Что требуется представить

1. Таблицу времени завершения `cpu-local` при `nice = 0` и `nice = 10` с конкурентом и без него.
2. Команду `renice`, идентификатор изменённого рабочего потока и наблюдение до/после изменения.
3. Объяснение, почему nice влияет на распределение CPU при конкуренции, но не является коэффициентом скорости процессора.

**Оценка: 30 баллов** — сравнение без/с конкуренцией (1),
корректное использование `renice` для TID (1), анализ результатов (1).

#### Серия C. Отзывчивость I/O-bound приложения — **30 баллов**

##### Эксперимент C1. Базовая задержка pipe

`io-pipe` состоит из двух процессов: Producer отправляет бинарные сообщения через stdout, Consumer получает их через stdin.
Producer большую часть времени ждёт следующего момента отправки, Consumer блокируется в `read()` до появления данных.

```bash
taskset -c "$CPU_B" build/release/bin/io-pipe \
    --producer --period-ms 10 --messages 300 |
  taskset -c "$CPU_A" build/release/bin/io-pipe --consumer
```

Producer выводит **служебные показатели в stderr** (они не передаются по pipe),
а Consumer — измеренные задержки в stdout.
Нельзя направлять произвольный текст в бинарный stdout Producer.

Используйте отдельные CPU для Producer и Consumer, если это позволяет среда.
Измерьте `latency_mean_ms`, `latency_p95_ms`, `latency_p99_ms`, `latency_max_ms`.

##### Эксперимент C2. Конкуренция за CPU

Запустите на `CPU_A` конкурирующую CPU-bound нагрузку (`cpu-local --threads 1 --duration-ms ...`) и повторите C1 так,
чтобы **Consumer и конкурент выполнялись на `CPU_A`, а Producer — на `CPU_B`**.

Убедитесь, что длительность конкурента превышает длительность серии отправок. Сравните задержки с базовым измерением.

##### Эксперимент C3. Политики планирования и nice

Повторите измерения Consumer при конкуренции за CPU в следующих конфигурациях:

| Конфигурация Consumer | Как запускать |
|---|---|
| `SCHED_OTHER`, nice 0 | `chrt -o 0 ...` |
| `SCHED_OTHER`, nice 10 | `nice -n 10 chrt -o 0 ...` |
| `SCHED_BATCH`, nice 0 | `chrt -b 0 ...` |
| `SCHED_IDLE`, nice 0 | `chrt -i 0 ...` |

Вместо `...` указывайте команду `taskset -c "$CPU_A" build/release/bin/io-pipe --consumer`.
Producer продолжает работать на другом CPU.

Для `SCHED_OTHER`, `SCHED_BATCH` и `SCHED_IDLE` аргумент статического приоритета равен **0**.
Политики реального времени `SCHED_FIFO` и `SCHED_RR` не требуются.
Если среда не позволяет установить одну из нужных политик, зафиксируйте ошибку и продолжите остальные эксперименты.

**Обязательно проверяйте также `wakeup_max_ms` в stderr Producer.**
Если Producer сам проснулся с большой задержкой, это влияет на интерпретацию результатов.
Измерение Consumer включает расходы pipe и ожидание CPU; оно **не равно** чистой задержке работы планировщика.
В режиме `SCHED_IDLE` возможны очень большие задержки, поэтому используйте конечное число сообщений
и ограниченное время фоновой нагрузки.

##### Что требуется представить

1. Таблицу средней, P95, P99 и максимальной задержки Consumer для разных конфигураций;
   также укажите максимальную задержку пробуждения Producer.
2. График P99-задержки для базового режима, режима с конкурентом и разных параметров Consumer.
3. Объяснение отличия CPU-bound от I/O-bound поведения и того,
   почему небольшая доля CPU не гарантирует низкой задержки обработки сообщения.

**Оценка: 30 баллов** — правильная изоляция Producer и конкуренция с Consumer (1),
измерения и график (1), сравнение политик и выводы (1).

#### Запуск автоматизированных примеров

В архиве есть скрипт `scripts/run-experiments.sh`.
Он **собирает Release-версию** и запускает примеры серий, записывая данные в CSV-файлы каталога `results/`:

```bash
scripts/run-experiments.sh info
scripts/run-experiments.sh scaling
scripts/run-experiments.sh priority
scripts/run-experiments.sh latency
# Или последовательно все серии:
scripts/run-experiments.sh all
```

По умолчанию скрипт выполняет три повтора.
Длительность нагрузки и число повторов регулируются переменными окружения. Например, для короткой пробной проверки:

```bash
REPEATS=1 LOCAL_ITERATIONS=10000000 SHARED_ITERATIONS=100000 \
  scripts/run-experiments.sh scaling
```

Скрипт автоматически выбирает первые разрешённые CPU из `/proc/self/status`.
Идентификаторы можно переопределить через `CPU_A` и `CPU_B`.
Для автоматического сценария `latency` требуются как минимум два разрешённых логических CPU.

**Скрипт — образец автоматизации, а не готовый отчёт.**
Студенты должны проверить параметры, самостоятельно объяснить результаты,
выполнить эксперимент B3 с `renice` и построить графики.
Если в автоматическом эксперименте конкурент завершился до исследуемой задачи, следует увеличить `PRIORITY_HOG_MS`.
