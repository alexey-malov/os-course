### Задание 1. — `isolated-runner` — **60 баллов**

Ознакомьтесь с системными вызовами [`fork(2)`](https://man7.org/linux/man-pages/man2/fork.2.html)
и [`waitpid(2)`](https://man7.org/linux/man-pages/man2/wait.2.html),
а также с механизмом завершения процессов в ОС Linux.

Напишите консольное приложение **`isolated-runner`**, которое запускает задания в отдельных дочерних процессах
и сообщает родителю, каким образом завершился каждый из них.

Цель задания — продемонстрировать, что **процесс является отдельной единицей выполнения и изоляции**:
аварийное завершение дочернего процесса не должно приводить к завершению родительского процесса или других дочерних процессов.

#### Что программа должна делать

Программа должна последовательно создать несколько дочерних процессов с помощью `fork()`.

Каждый дочерний процесс выполняет один из следующих сценариев:

- **Нормальное завершение**
  - вывести свой PID;
  - завершиться с кодом `0`.
- **Завершение с ненулевым кодом**
  - вывести свой PID;
  - завершиться с кодом `42`.
- **Аварийное завершение через `abort()`**
  - вывести свой PID;
  - вызвать `abort()`.
- **Аварийное завершение из-за недопустимого обращения к памяти**
  - вывести свой PID;
  - выполнить намеренно некорректное обращение к памяти, приводящее к завершению процесса операционной системой.

Каждый сценарий должен выполняться **в отдельном дочернем процессе**.

Родительский процесс не должен аварийно завершаться независимо от того, что произошло с ребёнком.

После завершения каждого дочернего процесса родитель должен определить причину его завершения
с помощью значения `status`, полученного от `waitpid()`.

#### Пример работы

Пример возможного вывода:

```text
Starting task: normal
Child 14321 started
Child 14321 exited with code 0

Starting task: exit-42
Child 14322 started
Child 14322 exited with code 42

Starting task: abort
Child 14323 started
Child 14323 terminated by signal 6 (Aborted)

Starting task: segfault
Child 14324 started
Child 14324 terminated by signal 11 (Segmentation fault)

All tasks completed
```

Конкретные PID и номера сигналов могут отличаться.

#### Требования к реализации

- Каждый сценарий должен запускаться с помощью отдельного вызова `fork()`.
- После `fork()` родитель должен ожидать завершения созданного дочернего процесса с помощью `waitpid()`.
- Необходимо корректно различать:
  - обычное завершение процесса;
  - завершение с ненулевым кодом;
  - завершение процесса сигналом.
- Для анализа статуса завершения используйте макросы:
  - `WIFEXITED(status)`;
  - `WEXITSTATUS(status)`;
  - `WIFSIGNALED(status)`;
  - `WTERMSIG(status)`.
- Если процесс завершён сигналом, программа должна вывести номер сигнала и, по возможности, его текстовое название.
- Все вызовы `fork()` и `waitpid()` должны проверяться на ошибки.
- `waitpid()` должен корректно обрабатывать прерывание системного вызова сигналом (`errno == EINTR`).
- Ошибка одного дочернего процесса не должна мешать запуску следующих заданий.
- После выполнения программы не должно оставаться дочерних процессов в состоянии zombie.

#### Коды возврата

- `0` — родительский процесс успешно запустил и дождался завершения всех заданий;
- `1` — родительский процесс не смог создать или корректно дождаться одного из дочерних процессов;
- `2` — ошибка использования программы, если она предусматривает аргументы командной строки.

Аварийное завершение одного из тестовых дочерних процессов само по себе
**не считается ошибкой программы `isolated-runner`**: это ожидаемая часть эксперимента.

#### Практическая часть: процесс-зомби

Измените программу так, чтобы перед вызовом `waitpid()` родительский процесс делал паузу на несколько секунд.

Например:

```text
Child 15240 has been started
Parent is waiting before waitpid()...
```

Пока родитель находится в состоянии ожидания:

1. найдите дочерний процесс из другого терминала с помощью `ps`;
2. определите его состояние;
3. убедитесь, что уже завершившийся, но ещё не обработанный родителем процесс находится в состоянии `Z` (Zombie);
4. после выполнения `waitpid()` повторно проверьте список процессов и убедитесь, что запись исчезла.

Для наблюдения можно использовать, например:

```bash
ps -o pid,ppid,state,cmd
```

или:

```bash
ps -el
```

Ответьте на вопросы:

1. Почему завершившийся процесс остаётся в таблице процессов до вызова `waitpid()`?
2. Какая информация о завершившемся процессе нужна его родителю?
3. Почему процесс в состоянии zombie практически не выполняет код, но всё ещё занимает запись в таблице процессов?
4. Почему отправка `SIGKILL` процессу-зомби не решает проблему?
5. Что произойдёт, если родительский процесс завершится, не вызвав `waitpid()`?

#### Бонус: несколько дочерних процессов — **+15 баллов**

Измените программу так, чтобы родитель сначала создал **все четыре дочерних процесса**,
а только затем начал ожидать их завершения.

Родитель не должен предполагать порядок, в котором дети завершатся.

Для ожидания используйте:

```cpp
waitpid(-1, &status, 0)
```

После каждого завершения выводите PID процесса и результат его работы.

Пример:

```text
Started child 16001: normal
Started child 16002: exit-42
Started child 16003: abort
Started child 16004: segfault

Child 16003 terminated by signal 6 (Aborted)
Child 16001 exited with code 0
Child 16004 terminated by signal 11 (Segmentation fault)
Child 16002 exited with code 42
```

Порядок завершения процессов может отличаться от порядка их создания.

Программа должна дождаться **всех** созданных детей и не оставить процессов-зомби.

#### Подсказки

- `fork()` возвращает разные значения в родительском и дочернем процессах:
  - `-1` — ошибка;
  - `0` — выполняется дочерний процесс;
  - положительное значение — выполняется родитель, а возвращённое значение является PID ребёнка.
- Для завершения дочернего процесса можно использовать `_exit()` или `std::_Exit()`.
- После аварийного завершения ребёнка выполнение родителя продолжается независимо от него.
- `waitpid()` возвращает PID процесса, состояние которого было получено.
- Не пытайтесь определять результат дочернего процесса только по возвращаемому значению `waitpid()`:
  - причина завершения находится в параметре `status`.
- Для получения текстового описания сигнала можно использовать `strsignal()`.
- Не полагайтесь на конкретные числовые значения `SIGABRT` и `SIGSEGV`: используйте соответствующие именованные константы.
- При выводе перед `fork()` учитывайте буферизацию `stdout`:
  невыведенные данные могут оказаться скопированы в буфер дочернего процесса.

### Задание 2 — `process-controller` — **60 баллов**

Ознакомьтесь с механизмом сигналов в ОС Linux и функциями `sigaction(2)` и `kill(2)`.

Напишите консольное приложение **`process-controller`**,
которое создаёт дочерний процесс и позволяет управлять его выполнением с помощью сигналов.

Цель задания — научиться использовать сигналы как механизм **асинхронного управления другим процессом**:
приостанавливать и возобновлять его выполнение, запрашивать состояние и корректно завершать работу.

---

#### Что программа должна делать

После запуска `process-controller` создаёт один дочерний процесс с помощью `fork()`.

Родительский процесс выполняет роль **контроллера**, а дочерний — роль **worker-процесса**.

Общая схема программы:

```text
┌──────────────────────┐       signals       ┌──────────────────────┐
│ process-controller   │ ──────────────────► │        worker        │
│                      │                     │                      │
│ читает команды       │                     │ выполняет работу     │
│ пользователя         │                     │ и хранит состояние   │
└──────────────────────┘                     └──────────────────────┘
```

После запуска программа должна вывести PID созданного worker-процесса и перейти в интерактивный режим:

```text
Worker started with PID 15231

> 
```

Контроллер должен поддерживать следующие команды:

```text
status
pause
resume
stop
```

---

#### Работа worker-процесса

Worker должен имитировать длительно работающий процесс.

Например, примерно один раз в секунду он увеличивает внутренний счётчик выполненных итераций:

```text
Worker 15231: iteration 1
Worker 15231: iteration 2
Worker 15231: iteration 3
...
```

Конкретная полезная работа несущественна.
Не следует выполнять вычисления, которые постоянно загружают одно ядро CPU на 100%.

Worker должен продолжать работу до получения команды на завершение.

---

#### Команда `pause`

При вводе:

```text
> pause
```

контроллер должен отправить worker-процессу сигнал `SIGSTOP`:

```cpp
kill(worker_pid, SIGSTOP);
```

Worker должен немедленно приостановить выполнение.

Например:

```text
Worker 15231: iteration 15
Worker 15231: iteration 16
> pause
Worker 15231 paused
```

После этого значение счётчика не должно изменяться до получения команды `resume`.

Обрабатывать `SIGSTOP` в самом worker-процессе не требуется.

---

#### Команда `resume`

При вводе:

```text
> resume
```

контроллер должен отправить worker-процессу сигнал `SIGCONT`.

Worker должен продолжить работу с того состояния, в котором он был приостановлен:

```text
> resume
Worker 15231 resumed
Worker 15231: iteration 17
Worker 15231: iteration 18
```

---

#### Команда `status`

При вводе:

```text
> status
```

контроллер должен отправить worker-процессу сигнал `SIGUSR1`.

Worker должен обработать этот сигнал и вывести своё текущее состояние, например:

```text
Worker 15231: iterations=23
```

Для установки обработчика используйте:

```cpp
sigaction()
```

а не устаревшую функцию `signal()`.

#### Важное требование

Не выполняйте сложную работу непосредственно внутри обработчика сигнала.

В частности, из обработчика `SIGUSR1` не следует вызывать:

```cpp
std::cout
printf
new
malloc
```

и другие функции, которые не гарантированы как async-signal-safe.

Обработчик должен только сохранить факт получения сигнала, например:

```cpp
volatile sig_atomic_t status_requested = 0;
```

а основная часть worker-процесса должна позднее проверить этот флаг и вывести состояние обычным способом.

---

#### Команда `stop`

При вводе:

```text
> stop
```

контроллер должен отправить worker-процессу сигнал `SIGTERM`.

Worker должен **обрабатывать `SIGTERM` самостоятельно**, а не завершаться стандартным обработчиком операционной системы.

Обработчик должен сообщить основной части программы о необходимости завершения.

Worker должен корректно закончить текущую работу и завершиться.

Например:

```text
> stop
Worker 15231 is shutting down
Worker 15231 exited
```

После этого родитель должен получить статус завершения процесса с помощью `waitpid()` и завершить работу `process-controller`.

---

#### Пример работы

Один из возможных вариантов:

```text
$ ./process-controller
Worker started with PID 15231

Worker 15231: iteration 1
Worker 15231: iteration 2
Worker 15231: iteration 3

> status
Worker 15231: iterations=3

> pause
Worker 15231 paused

> status

> resume
Worker 15231 resumed
Worker 15231: iterations=3
Worker 15231: iteration 4
Worker 15231: iteration 5

> status
Worker 15231: iterations=5

> stop
Worker 15231 is shutting down
Worker 15231 exited
```

Обратите внимание: если worker находится в состоянии `SIGSTOP`, он не выполняет пользовательский код.
Поэтому сигнал `SIGUSR1`, отправленный во время паузы, может быть обработан только после продолжения процесса.

---

#### Требования к реализации

##### Создание процесса

- Worker должен создаваться с помощью `fork()`.
- При вызове `fork()` необходимо проверять на ошибку.
- Родитель должен сохранить PID созданного процесса.
- Worker и controller должны выполняться как разные процессы.

Использовать `exec()` в этом задании **не требуется**.

---

##### Работа с сигналами

Для отправки сигналов используйте:

```cpp
kill()
```

Для пользовательских обработчиков используйте:

```cpp
sigaction()
```

Необходимо использовать следующие сигналы:

| Команда  | Сигнал    | Назначение                 |
| -------- | --------- | -------------------------- |
| `pause`  | `SIGSTOP` | приостановить worker       |
| `resume` | `SIGCONT` | продолжить worker          |
| `status` | `SIGUSR1` | запросить состояние        |
| `stop`   | `SIGTERM` | корректно завершить worker |

Все вызовы `kill()` должны проверяться на ошибки.

---

##### Обработчики сигналов

Обработчики `SIGUSR1` и `SIGTERM` должны выполнять только минимальные действия.

Допускается, например, изменение переменных типа:

```cpp
volatile sig_atomic_t
```

Основная логика обработки события должна выполняться за пределами signal handler.

---

##### Ожидание процесса

После команды `stop` родитель должен дождаться завершения worker-процесса с помощью:

```cpp
waitpid()
```

Необходимо:

- проверять ошибки `waitpid()`;
- корректно обрабатывать `EINTR`;
- определить, завершился ли worker самостоятельно или был уничтожен сигналом;
- не оставлять процесс в состоянии zombie.

---

##### Ошибки пользователя

Если введена неизвестная команда:

```text
> hello
Unknown command: hello
```

контроллер должен продолжить работу.

Пустую строку можно игнорировать.

---

##### Неожиданное завершение worker-процесса

Контроллер не должен считать, что worker обязательно существует до команды `stop`.

Например, пользователь может из другого терминала выполнить:

```bash
kill -9 <worker-pid>
```

Если при последующей отправке сигнала `kill()` сообщает, что процесс больше не существует,
контроллер должен вывести понятное сообщение и завершить работу без аварийного завершения.

Проверьте его состояние:

1. во время обычной работы;
2. после команды `pause`;

4. Что произойдёт, если отправить `SIGUSR1`, пока worker остановлен?

7. Чем управление процессом через сигналы отличается от передачи данных через pipe или FIFO?

#### Дополнительное задание — внешнее управление — **+10 баллов**

Добавьте режим:

```bash
process-controller --attach <pid>
```

В этом режиме программа **не создаёт собственного worker-процесса**,
а управляет уже существующим процессом по указанному PID.

Например:

```bash
./worker
Worker PID: 17342
```

В другом терминале:

```bash
./process-controller --attach 17342
> pause
> resume
> status
> stop
```

Таким образом, controller и worker становятся полностью независимыми программами и не обязаны иметь отношение родитель–ребёнок.

Продумайте, что должен делать controller после команды `stop`,
если управляемый процесс не является его дочерним и поэтому его нельзя ожидать с помощью `waitpid()`.

---

#### Дополнительное задание — `SIGCHLD` — **+10 баллов**

Добавьте в controller обработку `SIGCHLD`.

Если worker завершился самостоятельно или был уничтожен извне, controller должен обнаружить это и корректно завершиться.

Например, если в другом терминале выполнить:

```bash
kill -9 15231
```

controller должен сообщить:

```text
Worker 15231 was terminated by signal 9
```

и завершить интерактивный режим.

Не выполняйте `std::cout` или другую сложную логику непосредственно в обработчике `SIGCHLD`.

#### Подсказки

- `kill(pid, signal)` не обязательно «убивает» процесс: функция используется для **отправки любого сигнала**.
- `SIGSTOP` и `SIGKILL` нельзя перехватить, заблокировать или проигнорировать.
- `SIGTERM`, в отличие от `SIGKILL`, можно обработать и использовать
  для корректного завершения процесса.
- После получения `SIGSTOP` процесс вообще не выполняет пользовательский
  код до получения `SIGCONT`.
- Системные вызовы могут завершаться с `errno == EINTR` из-за доставки сигнала.
- Для задержки между итерациями worker можно использовать `nanosleep()`.
- Не полагайтесь на то, что `sleep()` или `nanosleep()`
  обязательно отработает весь указанный интервал после получения сигнала.
- Для проверки существования процесса можно использовать `kill(pid, 0)`,
  но учитывайте возможную ошибку доступа.
- Числовые значения сигналов могут различаться между системами.
  Используйте `SIGTERM`, `SIGUSR1`, `SIGSTOP`, `SIGCONT`, а не числа вроде `15` или `10`.

### Задание 3 — `mini-shell` — (до **90 баллов**)

Ознакомьтесь с системными вызовами `fork(2)`, `exec(3)`, `waitpid(2)`, `pipe(2)` и `dup2(2)` в ОС Linux.

Напишите консольное приложение **`mini-shell`** — упрощённую командную оболочку,
которая читает команды пользователя из стандартного ввода,
запускает указанные программы в отдельных процессах
и умеет соединять несколько программ с помощью pipe.

Цель задания — изучить:

- создание дочерних процессов;
- запуск других программ с помощью семейства функций `exec`;
- ожидание завершения дочерних процессов;
- перенаправление стандартных потоков;
- организацию межпроцессного взаимодействия через anonymous pipe;
- устройство конвейеров (`pipeline`) в UNIX-подобных операционных системах.

Задание состоит из нескольких уровней. Каждый следующий уровень расширяет возможности предыдущего.

---

#### Уровень 1 — запуск команд — **30 баллов**

На первом уровне `mini-shell` должен запускать одну внешнюю программу с произвольным количеством аргументов.

После запуска программа выводит приглашение:

```text
$ ./mini-shell
> 
```

Пользователь вводит команду:

```text
> ls -la /tmp
```

`mini-shell` должен:

1. прочитать строку из стандартного ввода;
2. разбить её на имя программы и аргументы;
3. создать дочерний процесс с помощью `fork()`;
4. в дочернем процессе запустить программу с помощью `execvp()`;
5. в родительском процессе дождаться её завершения с помощью `waitpid()`;
6. после завершения программы снова вывести приглашение.

Например:

```text
$ ./mini-shell
> echo Hello
Hello
> uname -s
Linux
> sleep 2
> echo done
done
> exit
$
```

Команда:

```text
exit
```

должна завершать сам `mini-shell` и **не должна запускаться через `execvp()`**.

---

##### Ошибка запуска программы

Если указанная программа не существует или не может быть запущена:

```text
> some-nonexistent-program
mini-shell: some-nonexistent-program: No such file or directory
>
```

ошибка должна завершить только дочерний процесс.

Сам `mini-shell` должен продолжить работу и принимать следующие команды.

---

##### Статус завершения

После завершения дочернего процесса `mini-shell` должен определить способ его завершения.

Если программа завершилась с ненулевым кодом, допустимо вывести диагностическое сообщение:

```text
> /bin/false
Process 15342 exited with code 1
```

Если программа была завершена сигналом:

```text
Process 15343 terminated by signal 11
```

Для анализа `status`, полученного от `waitpid()`, используйте:

```cpp
WIFEXITED(status)
WEXITSTATUS(status)
WIFSIGNALED(status)
WTERMSIG(status)
```

---

#### Уровень 2 — pipeline из двух программ — ещё **30 баллов**

Добавьте поддержку оператора:

```text
|
```

который соединяет стандартный вывод одной программы со стандартным вводом другой программы.

Например:

```text
> ls -la | wc -l
17
```

или:

```text
> ps aux | grep ssh
```

Для команды:

```text
command1 | command2
```

должны быть созданы **два дочерних процесса** и один anonymous pipe:

```text
                         pipe
                 ┌─────────────────┐
                 │                 ▼
        ┌──────────────┐    ┌──────────────┐
        │   command1   │    │   command2   │
        │              │    │              │
        │ stdout ──────┼────► stdin        │
        └──────────────┘    └──────────────┘
```

Первый процесс должен:

- сохранить обычный `stdin`;
- перенаправить свой `stdout` в write-end pipe;
- запустить `command1` через `execvp()`.

Второй процесс должен:

- перенаправить свой `stdin` на read-end pipe;
- сохранить обычный `stdout`;
- запустить `command2` через `execvp()`.

Для перенаправления файловых дескрипторов используйте функцию:

```cpp
dup2()
```

---

##### Закрытие файловых дескрипторов

После настройки стандартных потоков каждый процесс должен закрыть все файловые дескрипторы pipe, которые ему больше не нужны.

Родительский процесс также должен закрыть обе свои копии файловых дескрипторов pipe.

Это обязательное требование.

Программа не должна зависать из-за оставленного открытым write-end pipe.

Например, команда:

```text
> echo hello | cat
```

должна вывести:

```text
hello
```

и завершиться.

---

##### Ожидание процессов

Родитель должен запустить **оба процесса до начала ожидания их завершения**.

Недопустима реализация вида:

```text
создать command1
дождаться command1
создать command2
```

Обе программы pipeline должны иметь возможность выполняться одновременно.

После создания обоих процессов родитель должен дождаться завершения каждого из них с помощью `waitpid()`.

---

#### Уровень 3 — pipeline произвольной длины — ещё **30 баллов**

Расширьте программу так, чтобы она поддерживала произвольное количество программ в одном pipeline.

Например:

```text
> cat input.txt | grep ERROR | sort | uniq -c
```

или:

```text
> ps aux | grep python | wc -l
```

Для pipeline из `N` команд необходимо создать:

- `N` дочерних процессов;
- `N - 1` pipe.

Например:

```text
> command1 | command2 | command3 | command4
```

должно соответствовать:

```text
             pipe 1              pipe 2              pipe 3
┌──────────┐        ┌──────────┐        ┌──────────┐        ┌──────────┐
│ command1 │───────►│ command2 │───────►│ command3 │───────►│ command4 │
└──────────┘        └──────────┘        └──────────┘        └──────────┘
```

Для процесса с номером `i`:

- если существует предыдущий pipe, его read-end должен стать `STDIN_FILENO`;
- если существует следующий pipe, его write-end должен стать `STDOUT_FILENO`;
- после вызовов `dup2()` процесс должен закрыть **все** исходные файловые дескрипторы всех pipe;
- затем выполнить соответствующую команду с помощью `execvp()`.

После создания всех процессов родитель должен:

1. закрыть все принадлежащие ему файловые дескрипторы pipe;
2. дождаться завершения всех дочерних процессов;
3. продолжить работу и вывести новое приглашение.

---

#### Синтаксис команд

В основной части задания требуется поддерживать только упрощённый синтаксис.

Слова разделяются пробельными символами.

Оператор `|` должен быть отдельным токеном.

Пример корректной команды:

```text
cat input.txt | grep ERROR | wc -l
```

Не требуется поддерживать:

```text
&&
||
;
&
*
?
$HOME
$(...)
`command`
```

Также не требуется полноценная поддержка shell quoting и escaping.

Например, обработка:

```text
echo "Hello world"
```

может отсутствовать.

В рамках основной части можно считать, что аргументы не содержат пробелов.

---

#### Обработка некорректного ввода

`mini-shell` не должен аварийно завершаться при некорректной команде.

Например:

```text
> | ls
mini-shell: invalid pipeline
```

```text
> ls |
mini-shell: invalid pipeline
```

```text
> ls | | wc
mini-shell: invalid pipeline
```

После ошибки программа должна вывести новое приглашение.

Пустые строки можно игнорировать.

#### Завершение по EOF

Если стандартный ввод достиг EOF, `mini-shell` должен корректно завершиться.

Например, при интерактивной работе пользователь может нажать `Ctrl+D`.

#### Требования к реализации

##### Процессы

Для запуска каждой внешней программы обязательно использовать:

```cpp
fork()
```

и одну из функций семейства:

```cpp
exec*
```

Рекомендуется использовать:

```cpp
execvp()
```

Для запуска команд и построения pipeline необходимо самостоятельно использовать
`fork()`, функции семейства `exec`, `pipe()`, `dup2()` и `waitpid()`.
Использование `system()`, `popen()` и других функций,
передающих создание процессов или pipeline командной оболочке, не допускается.

---

##### Pipe

Для организации pipeline используйте:

```cpp
pipe()
```

или `pipe2()`.

Нельзя:

- передавать промежуточные данные через временные файлы;
- самостоятельно копировать данные между процессами через родительский процесс;
- заменять anonymous pipe другими механизмами IPC.

Данные должны передаваться непосредственно между дочерними процессами через pipe.

---

##### Перенаправление

Для подключения pipe к стандартным потокам процесса используйте:

```cpp
dup2()
```

После успешного `dup2()` исходный файловый дескриптор должен быть закрыт, если он больше не нужен.

---

##### Ошибки системных вызовов

Необходимо проверять ошибки всех существенных системных вызовов:

```cpp
fork()
pipe()
dup2()
execvp()
close()
waitpid()
```

При ошибках выводите понятное сообщение в `stderr`.

`waitpid()` должен корректно обрабатывать:

```cpp
errno == EINTR
```

---

##### Завершение дочернего процесса

Если `execvp()` завершился ошибкой, дочерний процесс должен вывести сообщение об ошибке и завершиться через:

```cpp
_exit(...)
```

или:

```cpp
std::_Exit(...)
```

Не следует после неудачного `exec()` продолжать выполнять код родительского shell.

---

##### Управление ресурсами

После выполнения pipeline не должно оставаться:

- дочерних процессов;
- процессов-зомби;
- ненужных открытых файловых дескрипторов.

Все открытые pipe должны быть закрыты на соответствующих путях выполнения.

#### Подсказки

- Для одной команды удобно сначала сформировать массив аргументов для `execvp()`.
- Последний элемент массива `argv`, передаваемого в `execvp()`, должен быть `nullptr`.
- При создании pipeline удобно сначала разобрать всю строку на отдельные команды,
  а затем создать необходимое количество pipe.
- Для `N` процессов требуется `N - 1` pipe.
- После `fork()` ребёнок наследует открытые файловые дескрипторы родителя.
- Именно это свойство позволяет создать pipe **до `fork()`**,
  а затем использовать его в дочерних процессах.
- После успешного `exec()` открытые файловые дескрипторы по умолчанию сохраняются,
  поэтому запущенная программа получает уже настроенные `stdin` и `stdout`.
- `execvp()` самостоятельно ищет программу по каталогам, указанным в переменной окружения `PATH`.
- Не забывайте, что каждый вызов `pipe()` создаёт **два** файловых дескриптора.
- Родитель shell не должен участвовать в передаче данных между стадиями pipeline:
  его задача — создать процессы, настроить их соединения и дождаться завершения.

### Задание 4 — `event-service` — (до **90 баллов**)

Ознакомьтесь с механизмом **FIFO (named pipe)** в ОС Linux и системными вызовами `mkfifo(3)`, `open(2)`, `read(2)`, `write(2)` и `unlink(2)`.

Напишите две консольные программы:

- **`event-service`** — сервис, принимающий и сохраняющий события;
- **`event-send`** — клиент, отправляющий события сервису.

В отличие от anonymous pipe, который обычно используется между процессами, имеющими общего предка,
FIFO существует как объект файловой системы и позволяет обмениваться данными между **независимо запущенными процессами**.

Цель задания — изучить:

- создание и использование FIFO;
- взаимодействие независимых процессов;
- блокирующее поведение FIFO;
- передачу структурированных сообщений через поток байтов;
- особенности работы нескольких процессов-писателей;
- корректное управление ресурсами IPC.

Задание состоит из трёх уровней. Каждый следующий уровень расширяет предыдущий.

---

#### Уровень 1 — передача событий через FIFO — **30 баллов**

Программа `event-service` должна создать FIFO и ожидать сообщения от клиентов.

Путь к FIFO передаётся первым аргументом:

```bash
./event-service /tmp/oslab-events.fifo
```

После запуска сервис должен создать FIFO:

```text
/tmp/oslab-events.fifo
```

и перейти в режим ожидания событий.

Клиент запускается независимо, в другом терминале:

```bash
./event-send /tmp/oslab-events.fifo INFO "Application started"
```

Например:

```bash
./event-send /tmp/oslab-events.fifo INFO "Application started"
./event-send /tmp/oslab-events.fifo WARN "Configuration file is missing"
./event-send /tmp/oslab-events.fifo ERROR "Cannot open database"
```

Процессы `event-service` и `event-send` **не должны иметь родственных отношений**.
Клиент не должен создаваться сервисом через `fork()`.

Общая схема взаимодействия:

```text
┌────────────┐
│ event-send │──┐
└────────────┘  │
                │
┌────────────┐  │       /tmp/oslab-events.fifo
│ event-send │──┼────────────────────────────────►┌───────────────┐
└────────────┘  │                                 │ event-service │
                │                                 └───────┬───────┘
┌────────────┐  │                                         │
│ event-send │──┘                                         ▼
└────────────┘                                        events.log
```

---

##### Формат события

Каждое событие должно содержать как минимум:

- PID клиента;
- уровень события;
- текст сообщения.

Необходимо поддерживать следующие уровни:

```text
INFO
WARN
ERROR
```

Конкретный формат протокола выберите самостоятельно.

Например, логическое сообщение может выглядеть так:

```text
pid=18321
level=INFO
message=Application started
```

или передаваться в бинарной форме.

Максимальный размер текста сообщения должен быть ограничен и задокументирован.

---

##### Работа `event-service`

При получении события сервис должен:

1. разобрать сообщение;
2. добавить к нему текущие дату и время;
3. вывести событие в `stdout`;
4. добавить событие в файл `events.log`.

Например:

```text
2026-09-18 14:21:05 [INFO]  pid=18321 Application started
2026-09-18 14:21:09 [WARN]  pid=18354 Configuration file is missing
2026-09-18 14:21:14 [ERROR] pid=18381 Cannot open database
```

Сервис должен продолжать работу после завершения клиента и принимать новые подключения.

Например:

```text
terminal 1:
$ ./event-service /tmp/oslab-events.fifo
event-service: listening on /tmp/oslab-events.fifo

2026-09-18 14:21:05 [INFO] pid=18321 Application started
2026-09-18 14:21:09 [WARN] pid=18354 Configuration file is missing
```

```text
terminal 2:
$ ./event-send /tmp/oslab-events.fifo INFO "Application started"
$ ./event-send /tmp/oslab-events.fifo WARN "Configuration file is missing"
```

Каждый запуск `event-send` является отдельным процессом.

---

##### Завершение сервиса

Добавьте специальную команду клиента:

```bash
./event-send /tmp/oslab-events.fifo --shutdown
```

После её получения `event-service` должен:

1. закончить обработку уже полученного сообщения;
2. закрыть открытые файловые дескрипторы;
3. удалить созданный FIFO с помощью `unlink()`;
4. завершиться.

После нормального завершения:

```text
/tmp/oslab-events.fifo
```

не должен оставаться в файловой системе.

---

##### Если сервис не запущен

Клиент не должен бесконечно ожидать появления сервиса.

Если FIFO отсутствует:

```text
$ ./event-send /tmp/oslab-events.fifo INFO hello
event-send: service is not available
```

программа должна завершиться с ошибкой.

Если FIFO существует, но его read-end не открыт сервисом, клиент также должен корректно обработать эту ситуацию.

Для этого можно исследовать поведение:

```cpp
open(path, O_WRONLY | O_NONBLOCK)
```

и ошибку:

```text
ENXIO
```

#### Уровень 2 — ответ клиенту — ещё **30 баллов**

На первом уровне данные передаются только в одну сторону:

```text
client ─────► service
```

Расширьте протокол так, чтобы сервис мог отправить клиенту подтверждение:

```text
client ─────► service
client ◄───── service
```

Для этого каждый клиент должен создавать **собственный FIFO для ответа**.

Например:

```text
/tmp/event-service-18321.fifo
```

где `18321` — PID клиента.

Архитектура:

```text
                                      общий FIFO
┌──────────────┐              /tmp/oslab-events.fifo
│              │────────────────────────────────────►┌───────────────┐
│  event-send  │                                     │ event-service │
│              │◄────────────────────────────────────│               │
└──────────────┘      /tmp/event-service-18321.fifo  └───────────────┘
                       персональный FIFO клиента
```

Перед отправкой запроса клиент должен:

1. создать свой response FIFO;
2. включить его имя в запрос;
3. отправить запрос через общий FIFO сервиса;
4. дождаться ответа через свой FIFO;
5. удалить response FIFO перед завершением.

---

##### Ответ сервиса

После успешной обработки события клиент должен получить подтверждение.

Например:

```text
$ ./event-send /tmp/oslab-events.fifo INFO "Application started"
OK
```

Если запрос некорректен:

```text
ERROR invalid event level
```

Конкретный формат ответа выберите самостоятельно.

Рекомендуется добавить каждому запросу **идентификатор запроса**, который сервер возвращает в ответе.

Например:

```text
request=42
status=OK
```

Это позволяет однозначно связать запрос и ответ.

---

##### Ошибки

Программы должны корректно обрабатывать ситуации, когда:

- request FIFO отсутствует;
- response FIFO уже существует;
- клиент завершился до получения ответа;
- сервис не может открыть response FIFO клиента;
- сообщение имеет некорректный формат;
- указан неизвестный уровень события.

Ошибка одного клиента не должна приводить к завершению `event-service`.

#### Уровень 3 — несколько одновременных клиентов — **ещё 30 баллов**

На предыдущих уровнях клиенты можно было запускать последовательно.

Теперь `event-service` должен корректно работать, если несколько процессов одновременно пишут в общий FIFO.

Например:

```bash
for i in $(seq 1 20); do
    ./event-send /tmp/oslab-events.fifo INFO "message $i" &
done
wait
```

Сервис должен получить **20 отдельных корректных событий**.

Данные разных клиентов не должны смешиваться.

---

##### Атомарность записи

Несколько процессов могут одновременно выполнять:

```cpp
write()
```

в один FIFO.

POSIX гарантирует атомарность записи в pipe/FIFO, если размер одной записи не превышает значение:

```text
PIPE_BUF
```

Поэтому каждый запрос клиента должен целиком помещаться в `PIPE_BUF` и отправляться в общий FIFO **одним вызовом `write()`**.

Не допускается передавать один запрос следующим образом:

```text
write(header)
write(message)
write(other_data)
```

поскольку между этими записями другой клиент может успеть записать свои данные.

Правильная логическая схема:

```text
┌──────────────────────────────────────────────┐
│  header + payload + response FIFO + ...      │
└──────────────────────────────────────────────┘
                       │
                       │ один write()
                       ▼
                 request FIFO
```

Перед отправкой необходимо проверить, что размер запроса не превышает допустимого размера.

Для получения ограничения можно использовать `PIPE_BUF` или исследовать:

```cpp
fpathconf(fd, _PC_PIPE_BUF)
```

---

##### FIFO является потоком байтов

Даже если клиент отправил запрос одним `write()`, сервер не должен считать, что один вызов:

```cpp
read()
```

обязательно соответствует одному сообщению.

FIFO представляет собой **поток байтов**.

Например, один `read()` может получить:

```text
[request 1][request 2][part of request 3]
```

а следующий:

```text
[rest of request 3]
```

Поэтому протокол должен позволять определить границы сообщений.

Можно использовать, например:

```text
┌──────────────┬─────────────────────────┐
│ message_size │ message                 │
└──────────────┴─────────────────────────┘
```

или сообщения фиксированного размера.

Сервис должен корректно обрабатывать неполные чтения и сохранять ещё не разобранную часть данных до следующего `read()`.

---

##### Проверка конкурентной работы

Запустите не менее 20 клиентов одновременно:

```bash
for i in $(seq 1 20); do
    ./event-send /tmp/oslab-events.fifo INFO "message $i" &
done
wait
```

Проверьте:

- каждый клиент получил ответ;
- сервис получил каждое сообщение ровно один раз;
- данные разных запросов не смешались;
- в `events.log` присутствуют все события.

Порядок событий в журнале **не обязан совпадать** с порядком запуска клиентов.

---

#### Требования к `event-service`

Сервис должен:

- создавать FIFO с помощью `mkfifo()`;
- открывать и читать FIFO с помощью `open()` и `read()`;
- принимать сообщения от независимо запущенных процессов;
- корректно переживать подключение и отключение клиентов;
- не завершаться после того, как последний клиент закрыл FIFO;
- проверять корректность полученных сообщений;
- записывать события в `events.log`;
- корректно освобождать ресурсы;
- удалять свой FIFO при штатном завершении.

Если после отключения всех писателей `read()` возвращает `0`, сервис не должен считать это окончанием своей работы.

Продумайте один из вариантов:

- повторно открыть FIFO;
- держать дополнительный write-end FIFO открытым внутри сервиса.

Вы должны уметь объяснить выбранное решение.

---

#### Требования к `event-send`

Клиент должен:

- работать как отдельный независимо запускаемый процесс;
- не создавать `event-service`;
- не использовать `fork()` для организации связи с сервисом;
- открывать существующий FIFO;
- формировать запрос согласно разработанному протоколу;
- отправлять запрос через `write()`;
- на уровнях 2–3 создавать отдельный FIFO для ответа;
- удалять собственный FIFO перед завершением;
- корректно сообщать об отсутствии сервиса.

---

#### Управление FIFO

Необходимо различать:

```text
close(fd)
```

и:

```text
unlink(path)
```

`close()` закрывает файловый дескриптор конкретного процесса.

`unlink()` удаляет имя FIFO из файловой системы.

Программа не должна безусловно удалять произвольный существующий файл.

Если по указанному пути уже существует объект, необходимо проверить, является ли он FIFO.

Если там находится обычный файл:

```text
/tmp/oslab-events.fifo
```

`event-service` не должен удалять или перезаписывать его.

---

#### Ошибки системных вызовов

Необходимо проверять ошибки как минимум следующих операций:

```cpp
mkfifo()
open()
read()
write()
close()
unlink()
```

а также операций с файлом журнала.

Следует корректно обрабатывать `EINTR`.

Понятные диагностические сообщения выводите в `stderr`.

---

#### Ограничения

Использование других механизмов IPC вместо FIFO не допускается.

В частности, для обмена между `event-send` и `event-service` нельзя использовать:

- обычные файлы;
- sockets;
- shared memory;
- anonymous pipe;
- перенаправление через shell;
- сторонние библиотеки межпроцессного взаимодействия.

Цель задания — самостоятельно реализовать обмен именно через **named pipe (FIFO)**.

#### Подсказки

- FIFO создаётся с помощью:

```cpp
mkfifo()
```

- После создания он открывается обычным:

```cpp
open()
```

- `mkfifo()` создаёт объект файловой системы, но передача данных начинается только после открытия FIFO процессами.
- Для проверки типа существующего объекта можно использовать `stat()` и `S_ISFIFO()`.
- Не удаляйте через `unlink()` объект, если не убедились, что это созданный вашей программой FIFO.
- Для имени response FIFO удобно использовать PID клиента.
- Если имя строится на основе PID, учитывайте возможность существования старого FIFO
  после аварийного завершения предыдущего клиента.
- Общий FIFO имеет нескольких писателей, поэтому формат запроса должен учитывать конкурентную запись.
- Не путайте **атомарность `write()`** с понятием **границы сообщения при `read()`**.
- FIFO особенно полезен здесь именно потому, что `event-service` и `event-send`
  запускаются независимо и не обязаны иметь общих предков.

#### Вариант A — Linux daemon

Напишите программу **`eventd`**, которая запускает сервис приёма событий в фоновом режиме.

После запуска:

```bash
./eventd /tmp/oslab-events.fifo
```

процесс должен отделиться от терминала и продолжить работу независимо от запустившей его командной оболочки.

После возврата приглашения shell:

```text
$ ./eventd /tmp/oslab-events.fifo
eventd started
$
```

daemon должен продолжать работать:

```bash
./event-send /tmp/oslab-events.fifo INFO "Application started"
```

Событие должно быть записано в журнал, даже если терминал, из которого был запущен `eventd`, уже закрыт.

---

##### Создание daemon

При запуске `eventd` должен выполнить процедуру daemonization.

Необходимо:

1. создать дочерний процесс с помощью `fork()`;
2. завершить исходный родительский процесс;
3. создать новую сессию с помощью:

  ```cpp
  setsid()
  ```

4. гарантировать, что daemon не связан с управляющим терминалом;
5. установить подходящее значение `umask`;
6. сменить текущий рабочий каталог на заранее определённый каталог, например:

  ```text
  /
  ```

или каталог данных сервиса;

7. закрыть унаследованные файловые дескрипторы, которые daemon не должен использовать;
8. корректно обработать стандартные потоки:

  ```text
  stdin
  stdout
  stderr
  ```

После daemonization процесс не должен зависеть от терминала, из которого он был запущен.

Допускается использование классической схемы с **двойным `fork()`**.

Вы должны уметь объяснить назначение каждого этапа daemonization.

---

##### PID-файл

После успешного запуска daemon должен создать PID-файл.

Например:

```text
/tmp/eventd.pid
```

Файл должен содержать PID daemon-процесса:

```text
18432
```

PID-файл используется для определения работающего экземпляра сервиса.

При корректном завершении daemon должен удалить PID-файл.

Daemon не должен безусловно запускать второй экземпляр, если уже существует работающий экземпляр `eventd`,
использующий тот же FIFO.

Не следует считать существование PID-файла достаточным доказательством того, что процесс действительно работает:
PID-файл мог остаться после аварийного завершения.

---

##### Журналирование

После отделения от терминала daemon не должен использовать обычный `stdout` для основного вывода.

Все рабочие и диагностические сообщения должны записываться:

- либо в собственный log-файл;
- либо через системный механизм журналирования.

Например:

```text
/var/tmp/eventd.log
```

или другой путь, не требующий привилегий `root`.

Пример:

```text
2026-09-18 10:15:01 eventd started pid=18432
2026-09-18 10:15:12 [INFO] pid=18501 Application started
2026-09-18 10:16:45 [WARN] pid=18524 Configuration file is missing
2026-09-18 10:17:03 eventd shutting down
```

Путь к журналу должен быть задокументирован.

---

##### Корректное завершение

Daemon должен обрабатывать:

```text
SIGTERM
```

как запрос на штатное завершение.

Например:

```bash
kill -TERM $(cat /tmp/eventd.pid)
```

После получения `SIGTERM` daemon должен:

1. прекратить принимать новые запросы;
2. завершить текущую операцию;
3. закрыть FIFO;
4. закрыть файл журнала;
5. удалить созданный FIFO;
6. удалить PID-файл;
7. завершиться с кодом `0`.

Не выполняйте всю логику завершения непосредственно внутри signal handler.

Обработчик сигнала должен только сообщить основной части программы о необходимости завершения.

---

##### Повторное открытие журнала по `SIGHUP`

Добавьте обработку:

```text
SIGHUP
```

После получения этого сигнала daemon должен закрыть текущий файл журнала и открыть его заново.

Например:

```bash
mv /var/tmp/eventd.log /var/tmp/eventd.log.old
kill -HUP $(cat /tmp/eventd.pid)
```

После этого новые события должны записываться в новый:

```text
/var/tmp/eventd.log
```

Это имитирует механизм **log rotation**, используемый реальными системными службами.

Обработчик `SIGHUP` не должен самостоятельно выполнять файловые операции. Он должен только установить соответствующий флаг.

#### Вариант B — Windows Service

Вместо Linux daemon можно реализовать **`event-service` как Windows Service**.

Служба должна запускаться и останавливаться через **Service Control Manager (SCM)**.

После установки службы она должна работать независимо от пользовательского терминала
и принимать запросы клиентов через Windows Named Pipe.

---

##### Регистрация службы

Программа должна поддерживать установку и удаление службы либо предоставлять отдельный способ сделать это.

Например:

```text
event-service install
event-service uninstall
```

Для работы с Service Control Manager ознакомьтесь с функциями:

```cpp
OpenSCManager()
CreateService()
OpenService()
DeleteService()
StartService()
ControlService()
```

Необходимо корректно проверять ошибки Windows API.

---

##### Запуск через Service Control Manager

При запуске как служба программа должна зарегистрировать точку входа через:

```cpp
StartServiceCtrlDispatcher()
```

и реализовать функцию службы:

```cpp
ServiceMain()
```

Служба должна зарегистрировать обработчик управляющих команд с помощью:

```cpp
RegisterServiceCtrlHandlerEx()
```

или соответствующего API.

---

##### Состояния службы

Служба должна корректно сообщать SCM свои состояния.

Как минимум:

```text
SERVICE_START_PENDING
SERVICE_RUNNING
SERVICE_STOP_PENDING
SERVICE_STOPPED
```

При нормальном запуске последовательность должна быть примерно такой:

```text
START_PENDING
      ↓
RUNNING
      ↓
STOP_PENDING
      ↓
STOPPED
```

Не следует сообщать `SERVICE_RUNNING`, пока служба ещё не готова принимать запросы клиентов.

---

##### Остановка службы

При получении управляющей команды:

```text
SERVICE_CONTROL_STOP
```

служба должна начать штатное завершение.

Она должна:

1. прекратить принимать новые запросы;
2. корректно завершить текущую обработку;
3. закрыть Named Pipe;
4. закрыть файлы журнала;
5. освободить все HANDLE;
6. сообщить SCM состояние `SERVICE_STOPPED`.

Сложную логику завершения не следует выполнять непосредственно внутри обработчика управляющей команды.

Обработчик должен только уведомить основной код службы о необходимости завершения, например через Event.

---

##### Использование Event для управления службой

Для передачи команды остановки из обработчика SCM в основной цикл службы используйте Windows Event.

Например:

```cpp
CreateEvent()
SetEvent()
WaitForSingleObject()
```

или:

```cpp
WaitForMultipleObjects()
```

Таким образом, основной цикл может одновременно ожидать:

* события от клиентов;
* команды остановки службы.

---

##### Журналирование

Windows Service не должен зависеть от консольного `stdout`.

Диагностические сообщения должны записываться:

- в log-файл;
- либо, в качестве усложнения, в Windows Event Log.

В журнале должны присутствовать как минимум:

- запуск службы;
- успешная готовность к работе;
- входящие события;
- ошибки;
- начало остановки;
- завершение службы.

Независимо от выбранной ОС служба должна обладать следующими свойствами:

##### Linux

- После `fork()` исходный родитель обычно завершается, а ребёнок продолжает daemonization.
- `setsid()` создаёт новую сессию и отсоединяет процесс от управляющего терминала.
- `SIGKILL` нельзя обработать, поэтому при таком завершении daemon не сможет выполнить очистку.
- Для флагов, устанавливаемых signal handler, можно использовать `volatile sig_atomic_t`.
- Не выполняйте `std::ofstream`, `printf`, `malloc` и другую сложную работу непосредственно из signal handler.
- При разработке удобно сначала реализовать сервис в foreground-режиме и только после этого добавлять daemonization.
- Для отладки полезно сохранить режим:

  ```bash
  ./eventd --foreground
  ```

в котором программа не отделяется от терминала.

##### Windows

- HANDLE следует освобождать на всех путях выполнения.
- Для управления временем жизни ресурсов удобно использовать RAII.
- Service Control Handler должен завершаться быстро.
- Длительную обработку выполняйте в основном потоке службы.
- Event хорошо подходит для передачи основному потоку команды остановки.
