## Цель работы

Научиться использовать динамические библиотеки для создания модульных приложений,
повторного использования программных компонентов и расширения функциональности программ без их перекомпиляции.

В ходе лабораторной работы вы познакомитесь с тремя сценариями применения динамических библиотек:

1. **Использование сторонней библиотеки** — подключение готовой динамической библиотеки к собственному приложению.
2. **Совместное использование библиотеки** — разработка динамической библиотеки,
   функциональность которой используется двумя независимыми приложениями.
3. **Разработка системы плагинов** — создание приложения, функциональность которого можно расширять подключением
   новых динамических библиотек во время выполнения.

|---|---:|---:|
| 1. Использование сторонней библиотеки zlib | 50 | +20 |
| 2. Общая динамическая библиотека для двух приложений | 100 | +20 |
| 3. Приложение с поддержкой плагинов | 150 | +40 |
| **Итого** | **300** | **+80** |

Задания независимы друг от друга. Бонусные баллы начисляются сверх базовой оценки за соответствующее задание.

## Общие требования

Для выполнения работы используйте C++17 или более новую версию языка.

Проекты должны собираться при помощи CMake и предусматривать возможность сборки под Linux и/или Windows.
Допускается кроссплатформенная реализация.
В этом случае платформенно-зависимый код должен быть отделён при помощи условной компиляции или отдельных файлов реализации.

Под Linux используются динамические библиотеки `.so`, под Windows — `.dll`.

При выполнении всех заданий необходимо учитывать следующие требования:

- Динамические библиотеки должны оставаться отдельными бинарными файлами.
  Замена динамической компоновки статической не допускается.
- Приложения должны корректно обрабатывать ошибки, которые могут возникнуть при выполнении предусмотренных операций.
- Ресурсы должны освобождаться корректно.
  Рекомендуется применять RAII для управления памятью, файловыми дескрипторами и загруженными библиотеками.
- При проектировании бинарных интерфейсов необходимо учитывать ABI, соглашения о вызовах функций,
  декорирование имён и правила владения памятью.
- Использовать готовые фреймворки для построения систем плагинов запрещается.

Проверка работоспособности как минимум в одной из поддерживаемых ОС обязательна.
Исходный код и конфигурация сборки должны предусматривать обе платформы.

## Задание 1. Использование сторонней динамической библиотеки zlib — **50 баллов**

### Постановка задачи

Разработайте консольную утилиту `file-compressor`, позволяющую сжимать и распаковывать файлы при помощи сторонней библиотеки **zlib**.

Библиотека должна использоваться в виде динамической библиотеки, установленной отдельно от исходного кода вашего приложения.

В этом задании не требуется самостоятельно реализовывать алгоритм сжатия.
Основная задача — научиться подключать сторонние динамические библиотеки,
использовать их API и обеспечивать наличие необходимых зависимостей при запуске приложения.

### Требования к функциональности

Программа должна поддерживать две команды.

**1. Сжатие файла**

```bash
file-compressor compress input.txt output.gz
```

Программа читает содержимое входного файла, сжимает его при помощи zlib и сохраняет результат в указанном выходном файле.

**2. Распаковка файла**

```bash
file-compressor decompress output.gz restored.txt
```

Программа распаковывает содержимое архива и восстанавливает исходный файл.

Для упрощения задания используйте формат **gzip**. Один архив должен содержать данные одного файла.
Реализовывать контейнер ZIP не требуется.

Для реализации можно использовать функции zlib:

- `gzopen` — открытие gzip-файла;
- `gzread` — чтение и распаковка данных;
- `gzwrite` — сжатие и запись данных;
- `gzclose` — закрытие файла;
- `gzerror` — получение информации об ошибках.

Обработка должна выполняться блоками ограниченного размера, чтобы программа могла работать с файлами,
которые не помещаются целиком в оперативную память.

Программа должна корректно обрабатывать пустые файлы, бинарные данные, отсутствие входного файла,
ошибки чтения и записи, а также повреждённые gzip-архивы.

Обратите внимание: некоторые функции zlib допускают чтение несжатых данных.
Поэтому при выполнении команды `decompress` необходимо проверять,
что входной файл действительно имеет ожидаемый формат gzip.

При возникновении ошибки программа должна возвращать ненулевой код завершения и выводить понятное сообщение.

### Требования к сборке

Для поиска библиотеки используйте CMake и `find_package(ZLIB REQUIRED)`.

Подключение библиотеки должно выполняться через импортируемую цель `ZLIB::ZLIB`.

Необходимо убедиться, что приложение использует именно динамическую библиотеку, а не статически включённую реализацию zlib.

**Успешная сборка с `ZLIB::ZLIB` сама по себе не подтверждает динамическую компоновку.**
Тип фактически используемой библиотеки необходимо проверить.

Для этого можно использовать:

- Linux: `ldd`, `readelf -d`;
- Windows: `dumpbin /DEPENDENTS`, Dependencies или Process Explorer.

### Развёртывание приложения

Подготовьте каталог для распространения приложения, содержащий исполняемый файл и необходимую динамическую библиотеку zlib.

Приложение должно запускаться без необходимости устанавливать zlib отдельно в системные каталоги целевой машины.

Для Linux допускается размещение библиотеки в подкаталоге `lib` с соответствующей настройкой `RPATH`/`RUNPATH`.
Для Windows DLL можно разместить рядом с исполняемым файлом.

Необходимо убедиться, что при запуске используется именно подготовленная динамическая библиотека,
а не случайно найденная системная копия.

Переносимость проверяется в пределах совместимой ОС и архитектуры процессора. Упаковывать системные компоненты ОС не требуется.

### Проверка работоспособности

Продемонстрируйте:

1. Сжатие обычного текстового файла.
2. Сжатие и восстановление бинарного файла, содержащего в том числе нулевые байты.
3. Сжатие и восстановление пустого файла.
4. Обработку повреждённого gzip-архива.
5. Запуск приложения из подготовленного каталога с локально размещённой библиотекой zlib.

После распаковки восстановленный файл должен **побайтово совпадать с исходным**.

### Бонусные требования

#### Бонус 1. Информация о библиотеке — **+5 баллов**

Добавьте команду `info`, которая выводит:

- версию zlib, использованную при компиляции приложения;
- версию zlib, фактически загруженной во время выполнения.

Используйте `ZLIB_VERSION` и `zlibVersion()`.

#### Бонус 2. Управление степенью сжатия — **+5 баллов**

Добавьте возможность указывать уровень сжатия от 0 до 9.

Продемонстрируйте влияние уровня сжатия на размер результата для нескольких файлов с различным содержимым.

#### Бонус 3. Автоматизированные интеграционные тесты — **10 баллов**

Добавьте тесты, которые автоматически сжимают и распаковывают набор файлов
и проверяют побайтовое совпадение восстановленных данных с исходными.

Тесты должны запускаться через CTest или отдельный тестовый скрипт.

## Задание 2. Общая динамическая библиотека для двух приложений — **100 баллов**

### Постановка задачи

Разработайте два независимых консольных приложения, которые используют **одну общую динамическую библиотеку**.

В качестве предметной области предлагается контроль целостности файлов.

Необходимо реализовать:

- `manifest-create` — приложение для создания манифеста контрольных сумм файлов;
- `manifest-verify` — приложение для проверки файлов по ранее созданному манифесту;
- `integrity-core` — общую динамическую библиотеку, содержащую реализацию алгоритма вычисления контрольных сумм.

Оба приложения должны использовать функции одной библиотеки, но выполнять разные пользовательские задачи.

### Общая динамическая библиотека

Библиотека `integrity-core` должна предоставлять интерфейс для вычисления контрольной суммы данных.

Для этого предлагается реализовать алгоритм **CRC32**.

В первой версии библиотеки допускается использование простой побитовой реализации CRC32.
Алгоритм должен находиться именно в общей библиотеке.
Запрещается дублировать его реализацию в приложениях или заменять вызовом сторонней библиотеки.

Самостоятельно спроектируйте публичный интерфейс библиотеки. При проектировании учитывайте:

- совместимость с C ABI;
- представление типов данных на границе модулей;
- правила передачи буферов и размеров данных;
- обработку ошибок;
- возможность изменения внутренней реализации без изменения интерфейса.

Допускается использовать C++ и стандартную библиотеку внутри `integrity-core`.
При этом не следует передавать через публичный интерфейс объекты со сложной C++ ABI, такие как `std::string` и `std::vector`.

### Приложение manifest-create

Программа должна принимать список файлов и создавать текстовый манифест с информацией о них.

Пример использования:

```bash
manifest-create -o manifest.txt file1.txt file2.bin
```

Манифест должен содержать как минимум:

- путь или имя файла;
- размер файла;
- контрольную сумму CRC32.

Формат манифеста необходимо описать в документации проекта.

Для вычисления контрольных сумм приложение обязано использовать функции динамической библиотеки `integrity-core`.

### Приложение manifest-verify

Программа должна принимать манифест и проверять перечисленные в нём файлы.

Пример:

```bash
manifest-verify manifest.txt
```

Пример результата:

```text
file1.txt   OK
file2.bin   MODIFIED
file3.txt   MISSING
```

Статусы означают:

- `OK` — файл существует, его размер и контрольная сумма совпадают с манифестом;
- `MODIFIED` — содержимое файла не соответствует манифесту;
- `MISSING` — файл отсутствует.

Приложение должно различать отсутствие файла и ошибку чтения. Для непредвиденных ошибок допускается отдельный статус `ERROR`.

Вычисление CRC32 должно выполняться через ту же динамическую библиотеку, что и в `manifest-create`.

Важно: CRC32 позволяет обнаруживать случайные изменения данных, но не предназначен для криптографической проверки подлинности файлов.

### Требования к динамической компоновке

Создайте библиотеку `integrity-core` как отдельную цель CMake типа `SHARED`.

Оба приложения должны быть динамически скомпонованы с этой библиотекой стандартными средствами компоновщика.

Использовать `dlopen`, `LoadLibrary` и аналогичные функции в этом задании не требуется.

После сборки необходимо получить два исполняемых файла и одну общую динамическую библиотеку, доступную обоим приложениям.

Не допускается создание двух независимых копий библиотеки — по одной для каждого приложения.

Продемонстрируйте, что оба приложения действительно используют одну динамическую библиотеку.

### Независимое обновление библиотеки

Реализуйте две версии библиотеки `integrity-core`.

**Версия 1:** простая побитовая реализация CRC32.

**Версия 2:** оптимизированная реализация CRC32 с использованием предварительно вычисленной таблицы.

Обе версии должны вычислять одинаковые контрольные суммы и предоставлять бинарно совместимый интерфейс.

Порядок выполнения эксперимента:

1. Соберите оба приложения с первой версией библиотеки.
2. Проверьте корректность создания и проверки манифеста.
3. Соберите вторую версию библиотеки.
4. Замените первую версию библиотеки второй, предварительно завершив работающие приложения.
5. Запустите исходные исполняемые файлы без их перекомпиляции.
6. Убедитесь, что оба приложения продолжают корректно работать.

В отчёте необходимо объяснить, почему обновление реализации не потребовало пересборки приложений
и какие изменения публичного ABI могли бы нарушить совместимость.

### Эксперимент с памятью процессов

Продемонстрируйте, что оба приложения могут использовать общие физические страницы машинного кода библиотеки,
но при этом сохраняют независимые изменяемые данные.

Для исследования загрузите оба приложения одновременно и предусмотрите возможность оставить их запущенными на время анализа.

В Linux можно использовать `/proc/<pid>/maps`, `/proc/<pid>/smaps`.

В Windows — Process Explorer и VMMap.

Найдите отображения общей динамической библиотеки в адресных пространствах обоих процессов.
Исследуйте отображения кода и изменяемых данных.
Объясните, какие страницы потенциально могут совместно использоваться, а какие должны оставаться частными.

Учтите, что совпадение имени отображённого файла само по себе не является
доказательством использования одной физической страницы.

#### Эксперимент с глобальной переменной

Добавьте в `integrity-core` глобальный счётчик вызовов, а также экспортируемую функцию, позволяющую получать или увеличивать его значение.

Продемонстрируйте, что два одновременно работающих процесса имеют независимые значения счётчика.

Объясните, почему совместное использование динамической библиотеки не приводит к совместному использованию
её обычных глобальных переменных между процессами.

### Бонусные требования

#### Бонус 1. Версионирование библиотеки — **+10 баллов**

Реализуйте осмысленное версионирование динамической библиотеки.

В Linux используйте механизм `SONAME` и версии файлов `.so`. Для Windows предусмотрите соответствующую версию DLL.

Продемонстрируйте, как приложение определяет требуемую версию библиотеки и что происходит при отсутствии совместимой версии.

#### Бонус 2. Расширение ABI без нарушения совместимости — **+10 баллов**

Добавьте в библиотеку новую публичную функцию, сохранив работоспособность ранее собранных приложений.

Разработайте небольшой клиент, использующий новый функционал, и покажите,
что старые приложения продолжают работать с обновлённой библиотекой.

## Задание 3. Приложение с поддержкой плагинов — **150 баллов**

### Постановка задачи

Разработайте консольное приложение `plugin-host`,
функциональность которого расширяется подключением динамических библиотек — плагинов.

Главное требование: **для добавления нового плагина не должна требоваться перекомпиляция основного приложения**.

В отличие от второго задания, здесь библиотеки должны загружаться явно во время выполнения программы:

- в Linux через `dlopen`, `dlsym`, `dlclose`;
- в Windows через `LoadLibrary` / `LoadLibraryEx`, `GetProcAddress`, `FreeLibrary`.

Самостоятельно спроектируйте систему плагинов, включая бинарный интерфейс, механизм обнаружения,
взаимодействие с хостом и управление временем жизни ресурсов.

Готовая спецификация интерфейса плагинов не предоставляется.

### Функциональность основного приложения

`plugin-host` должен находить плагины в заданном каталоге и предоставлять пользователю доступ к их функциям.

Пример структуры каталога:

```text
plugin-host/
├── plugin-host.exe
└── plugins/
    ├── stats.dll
    └── hex.dll
```

В Linux используются соответствующие исполняемые файлы и `.so` вместо `.dll`.

Основное приложение должно поддерживать как минимум две операции.

**1. Просмотр доступных плагинов**

```bash
plugin-host list
```

Пример:

```text
Available plugins:

stats   File statistics
hex     Hexadecimal file viewer
```

**2. Выполнение операции плагина**

```bash
plugin-host run stats example.txt
```

Пример:

```text
File: example.txt
Size: 1542 bytes
Lines: 28
Words: 187
```

Синтаксис дополнительных аргументов плагинов вы определяете самостоятельно.
Минимальные команды `list` и `run` должны быть доступны во всех реализациях.

### Разработка плагинов

Реализуйте минимум два плагина с различной функциональностью.

Рекомендуемые варианты:

**Плагин `stats`**

Анализирует текстовый файл и выводит:

- размер в байтах;
- количество строк;
- количество слов.

**Плагин `hex`**

Отображает содержимое бинарного файла в шестнадцатеричном представлении.

Для больших файлов можно ограничить вывод первыми 64 байтами, предусмотрев возможность изменения лимита через аргумент.

Плагины должны быть независимыми динамическими библиотеками.

Основное приложение не должно содержать реализацию их функций или зависеть от конкретных имён `stats` и `hex`.

Для добавления третьего плагина не должно требоваться изменение исходного кода `plugin-host`.

### Самостоятельное проектирование интерфейса плагинов

Разработайте собственный публичный ABI-контракт между приложением и плагинами.

Интерфейс должен обеспечивать:

1. Идентификацию плагина и получение информации о нём.
2. Определение совместимости версии интерфейса.
3. Передачу аргументов для выполнения операции.
4. Получение результата и информации об ошибках.
5. Корректное управление памятью и другими ресурсами.
6. Возможность независимой сборки новых плагинов.

Вы самостоятельно определяете набор экспортируемых функций, их сигнатуры и структуру используемых данных.

Для обеспечения совместимости рекомендуется экспортировать функции с C-linkage (`extern "C"`) и
использовать C-совместимые типы данных.

**Запрещается передавать через публичный интерфейс плагина объекты `std::string`, `std::vector` и другие сложные C++-объекты,**
**бинарное представление которых может зависеть от компилятора или стандартной библиотеки.**

Внутри приложения и плагинов использование любых подходящих средств C++ разрешается.

#### Передача строк и управление памятью

Как минимум один из плагинов должен возвращать текстовый результат переменного размера.

Необходимо самостоятельно выбрать и реализовать безопасный способ передачи такого результата через границу библиотеки.

Например, можно использовать:

- выделение памяти в библиотеке и освобождение через экспортируемую функцию этой же библиотеки;
- буфер, предоставленный основным приложением;
- callback-функцию для передачи результата приложению.

Выбранный контракт владения памятью необходимо описать в документации.

Если память выделяет плагин, основное приложение не должно освобождать её через несовместимый аллокатор.

Обратите внимание: использование `extern "C"` решает проблему C++-декорирования имён,
но не устраняет автоматически все проблемы ABI-совместимости.

### Обнаружение и загрузка плагинов

Основное приложение должно:

1. Находить в каталоге файлы с подходящим для текущей ОС расширением динамической библиотеки.
2. Пытаться загрузить найденные библиотеки.
3. Проверять наличие необходимых экспортируемых функций.
4. Получать информацию о плагинах.
5. Проверять совместимость интерфейсов.
6. Регистрировать успешно загруженные плагины.
7. Предоставлять пользователю возможность вызова их функций.

По умолчанию каталог `plugins` должен определяться относительно местоположения исполняемого файла, а не текущей рабочей директории.

Рекомендуется также предусмотреть возможность явно задать каталог плагинов через аргумент командной строки.

Для выполнения задания необходимо использовать платформенные API загрузки динамических библиотек.
Использование только обычной динамической компоновки через `target_link_libraries` недостаточно.

В CMake плагины должны собираться отдельно от основного приложения. Основное приложение не должно линковаться с конкретными плагинами.

### Обработка ошибок и совместимость

Приложение должно продолжать работу, если в каталоге плагинов обнаружена библиотека, которую невозможно использовать.

Предусмотрите обработку следующих ситуаций:

- файл не является корректной динамической библиотекой;
- библиотека не содержит обязательных экспортируемых функций;
- версия интерфейса плагина несовместима с версией интерфейса приложения;
- несколько плагинов используют одинаковый идентификатор;
- плагин сообщает об ошибке выполнения;
- пользователь пытается вызвать неизвестный плагин.

Недопустимо завершать работу всего приложения при обычной ошибке обнаружения,
загрузки или выполнения плагина, если ошибка может быть безопасно обработана.

При этом обеспечивать защиту от произвольного повреждения памяти внутри плагина не требуется.
Плагины выполняются в адресном пространстве основного процесса,
поэтому полностью изолировать их ошибки без дополнительных механизмов невозможно.

#### Управление временем жизни

Необходимо обеспечить корректную загрузку и выгрузку библиотек.

В частности:

- адреса функций должны использоваться только пока соответствующая библиотека загружена;
- ресурсы, принадлежащие плагину, должны освобождаться до выгрузки необходимого для их освобождения кода;
- не должны возникать утечки ресурсов при ошибке загрузки или инициализации;
- повторное уничтожение одного ресурса недопустимо.

Рекомендуется использовать RAII-обёртки для дескрипторов динамических библиотек.

### Проверка расширяемости

Самая важная проверка задания — подключение нового плагина без изменения основного приложения.

Порядок проверки:

1. Соберите `plugin-host` и два первоначальных плагина.
2. Убедитесь, что приложение обнаруживает оба плагина и корректно выполняет их операции.
3. Разработайте третий плагин, используя только публичный интерфейс и документацию вашей системы.
4. Соберите третий плагин отдельно от основного приложения.
5. Поместите его динамическую библиотеку в каталог `plugins`.
6. Запустите ранее собранный `plugin-host`.
7. Убедитесь, что новый плагин обнаруживается и его функциональность доступна.

**Пересобирать или изменять `plugin-host` между шагами 2 и 7 запрещается.**

Преподаватель может предложить дополнительную функциональность для проверочного плагина.

Ваш публичный интерфейс должен позволять разработать такой плагин без изучения внутренней реализации основного приложения.

### Демонстрационный проект

Для знакомства с механизмом динамической загрузки предоставляется проект `dynamic-library-demo`.

Он демонстрирует:

- загрузку DLL/.so из подкаталога;
- поиск экспортируемых функций по имени;
- вызов функций через указатели;
- передачу строк через C-совместимый интерфейс;
- использование функций `MakeString` и `FreeString`;
- применение RAII-обёрток `DynamicLibrary` и `LibraryString`.

Разрешается использовать приёмы и вспомогательные классы из демонстрационного проекта.

Однако проект не содержит готовой системы плагинов.
Интерфейс плагинов, механизм регистрации и архитектуру взаимодействия с хостом вы должны разработать самостоятельно.

### Бонусные требования

#### Бонус 1. Загрузка новых плагинов без перезапуска — **+15 баллов**

Реализуйте команду `reload`, которая повторно сканирует каталог плагинов.

Если в каталоге появились новые динамические библиотеки, приложение должно загрузить и зарегистрировать их без перезапуска.

Повторная загрузка уже зарегистрированных плагинов не должна создавать дубликаты.

Выгрузка старых плагинов для этого бонуса не требуется.

#### Бонус 2. Динамическая выгрузка плагинов — **+15 баллов**

Реализуйте возможность выгрузить выбранный плагин во время работы приложения.

Перед выгрузкой должны быть освобождены все связанные с ним ресурсы.
После выгрузки приложение не должно обращаться к указателям на функции или объекты из выгруженной библиотеки.

Если плагин ещё используется, приложение должно безопасно отклонить запрос на выгрузку или отложить её до освобождения ресурсов.

#### Бонус 3. Поддержка нескольких версий ABI — **+10 баллов**

Разработайте вторую версию публичного интерфейса плагинов.

Добавьте поддержку обеих версий в `plugin-host` и продемонстрируйте работу плагинов, использующих разные версии интерфейса.

При этом плагины, созданные для первой версии ABI, не должны требовать пересборки.

### Общие критерии проверки

При оценивании будет учитываться не только правильность вывода программы, но и выполнение архитектурных требований.

Например:

- Программа, использующая статическую zlib вместо динамической,
  не выполняет требование динамической компоновки задания 1.
- Два приложения, каждое из которых содержит собственную копию алгоритма CRC32,
  не выполняют требование общей библиотеки задания 2.
- Программа, в которой имена плагинов и их функции заранее прописаны в исходном коде,
  не выполняет требование расширяемости задания 3.
- Приложение, которое успешно вызывает функцию плагина, но допускает обращение к ней после выгрузки DLL/.so,
  нарушает требования управления временем жизни ресурсов.

Бонусные требования оцениваются только при корректной реализации соответствующих базовых механизмов.
