# Демонстрация динамической загрузки библиотек (Windows / Linux)

Небольшой CMake-проект для лабораторной работы по операционным системам. Приложение `demo-host` **не линкуется** с `string_plugin`: во время выполнения оно самостоятельно загружает DLL/.so из подкаталога `plugins`, находит экспортируемые функции и вызывает их.

## Структура проекта

```text
dynamic-library-demo/
├── CMakeLists.txt
├── common/
│   └── StringApi.h           # C ABI: MakeString, FreeString
├── library/
│   └── StringLibrary.cpp     # Реализация DLL/.so
└── host/
    ├── main.cpp             # Загрузка из каталога plugins/
    ├── DynamicLibrary.h/.cpp # RAII для LoadLibrary/dlopen
    └── LibraryString.h/.cpp  # RAII для строки из библиотеки
```

## Сборка и запуск в Linux

Нужны CMake 3.20+, компилятор с поддержкой C++17 и стандартный инструмент сборки.

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
./build/bin/Release/demo-host
ctest --test-dir build -C Release --output-on-failure
```

## Сборка и запуск в Windows

Для Visual Studio 2022 (x64) выполните из терминала с доступными инструментами сборки:

```powershell
cmake -S . -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release
.\build\bin\Release\demo-host.exe
ctest --test-dir build -C Release --output-on-failure
```

Проект также можно открыть напрямую в Visual Studio или CLion как CMake-проект. Тест Windows приведён для 64-разрядной сборки.

После сборки получаем:

```text
build/bin/Release/
├── demo-host[.exe]
└── plugins/
    └── [lib]string_plugin.[so|dll]
```

Исполняемый файл находит библиотеку **относительно своего местоположения**, а не текущей рабочей директории. Поэтому запуск работает и из другой папки.

## Что демонстрирует проект

1. **Динамическая загрузка.** В Linux используется `dlopen(..., RTLD_NOW | RTLD_LOCAL)`, в Windows — `LoadLibraryW`. Получение функции выполняется через `dlsym` или `GetProcAddress`.
2. **Отсутствие статической зависимости.** `demo-host` не вызывает функции библиотеки напрямую и не связывается с импортной библиотекой `.lib`. Имя файла и имена символов задаются строками в коде приложения.
3. **C ABI.** Библиотека экспортирует `extern "C"` функции `MakeString(const char*)` и `FreeString(char*)`. В Windows явно задан `__cdecl`.
4. **Владение памятью.** `MakeString` выделяет копию переданного текста внутри библиотеки. Вызывающая сторона должна освобождать её исключительно через `FreeString` из **той же загруженной библиотеки**.
5. **RAII.** `LibraryString::Make` заранее находит обе функции. Затем `LibraryString` хранит выделенную строку с указателем на `FreeString` в качестве deleter, а также `shared_ptr<DynamicLibrary>`. Это гарантирует, что `FreeString` выполнится до выгрузки библиотеки.
6. **Исключения не пересекают C ABI.** `MakeString` возвращает `nullptr` при невозможности выделить память. C++-исключения появляются только на стороне хоста, в его обёртках.

### Минимальный пример использования

```cpp
auto lib = std::make_shared<DynamicLibrary>(PluginPath());
auto text = LibraryString::Make(lib, "Hello!");
lib.reset(); // Библиотека НЕ выгружается: text ещё хранит shared_ptr.
std::cout << text.ToString() << '\n';
// После разрушения text вызывается FreeString, затем может выгрузиться библиотека.
```

Важно: `LibraryString` специально знает имена функций **этой конкретной библиотеки**. Это учебная вспомогательная обёртка, а не универсальный стандарт для любых плагинов. В самостоятельном задании студенты должны сами спроектировать свой ABI.

## Эксперименты

- Уберите DLL/.so из `plugins/` и запустите приложение: получите диагностическую ошибку загрузки.
- Переименуйте экспортируемую функцию `FreeString` в исходном коде библиотеки, пересоберите и посмотрите ошибку поиска символа.
- Замените текст, который передаётся в `LibraryString::Make`, и убедитесь, что приложение не нужно перелинковывать с плагином.
- Изучите символы библиотеки: Linux — `nm -D` или `readelf -Ws`; Windows — `dumpbin /EXPORTS`.

## Ограничения учебного примера

- Поддерживаются Windows и Linux на C++17; инструкции для Windows ориентированы на x64.
- Код передаёт UTF-8 как последовательность байтов и не выполняет преобразование кодировок.
- Это *одна заранее известная библиотека*, а не полноценная система обнаружения/регистрации плагинов. Именно разработка собственной системы расширений может стать самостоятельной лабораторной работой.
- Загруженный модуль исполняется в адресном пространстве процесса. RAII защищает от ошибок управления временем жизни, но не изолирует хост от ошибок внутри плагина.
